# Security and privacy audit notes

## 2026-08-08 beta.54 Durable Object quota incident and independent read-amplification review

The owner reported a Cloudflare Durable Objects Free-plan warning that the account had consumed 90% of its 5,000,000 daily `rows_read` allowance. This review did not assume the warning was historical or caused by unrelated workloads. After the 00:00 UTC reset, authenticated Cloudflare analytics for the current account showed 1,344,623 rows read and 13,918 rows written by approximately 03:31 UTC. A second read-only query at 04:05 UTC showed 1,417,559 rows read (28.35% of the 5,000,000 daily allowance) and 15,231 rows written, proving that the old live runtime continued accumulating the same cost while the repair was developed. The usage grouped to one active `BridgeRoom` Durable Object rather than multiple namespaces. During the same window the object handled roughly 7,515 successful hibernation events, 3,822 successful HTTP events, 3,407 `responseStreamDisconnected` HTTP events, and 354 alarms. At that average read rate the daily rows-read allowance would be exceeded again, while the write rate was already close enough to the free-tier write budget that a fix could not safely trade reads for a new globally rewritten index.

The live beta.50 `server_info` also proved that this was not an unused legacy compatibility path. The current host was actively completing legacy resumable durable calls and opening the internal hibernatable terminal subscribers. Source tracing then identified a systematic O(events x retained-streams) read pattern. `BridgeRoom.fetch()` and every hibernatable WebSocket message called `expireOverdueCalls()`, which unconditionally delegated to durable `expireDue()`. That operation enumerated every `mcp-stream:*` row. A normal legacy call separately enumerated the same rows for request-key deduplication, stream admission, call activation, alarm deadline discovery, and call-ID lookup. Beta.45 intentionally removed beta.44's globally rewritten `mcp-stream-index` to cure rows-written amplification, but making per-stream rows authoritative left too many unrelated event paths using full prefix enumeration. The current quota incident is the read-side consequence of that earlier write optimization.

Beta.54 keeps the per-stream authority and does not recreate a global index. Legacy stream admission and durable-call activation are instead one transaction over one bounded prefix-list snapshot: request identity, expiry pruning, capacity, call admission, and the initial active record all use that observation. Production no longer exposes a separate request-key full-scan helper. A lost `prepare` response remains safe because a retry runs the same transaction and returns the existing stream as `resume`; a different argument fingerprint returns `conflict` and never sends a second daemon call. Sessionless legacy requests intentionally retain independent generations. The hot production path also drops one stream mutation because the transient pending stream and active durable call are now published together.

New random streams and daemon call IDs share one random 43-character generation suffix while retaining distinct `stream_` and `call_` domains. The suffix is generated from the stream identity, not from the reusable JSON-RPC request ID, so acknowledging one request and intentionally reusing its request ID still creates an unrelated generation. Terminal call lookup derives the stream key and performs one point read. If that row exists but is already terminal, duplicate daemon results stop there. Only when the derived row is absent may a pre-beta.54 independent random call ID use one bounded migration prefix scan; those records age out under the existing pending/reconnect limits.

Deadline recovery is now alarm-led rather than event-scan-led. A future persisted runtime alarm is sufficient evidence that all already-existing durable deadlines are protected, so ordinary HTTP and WebSocket entry performs no durable prefix scan. New durable admission commits the active stream row and advances the persisted alarm to no later than the exact operation deadline inside the same Durable Object storage transaction. The event cannot therefore crash between durable ownership publication and alarm coverage; the later scheduler only coalesces daemon/transient deadlines and does not enumerate durable rows. Detach/rebind preserves or extends existing deadlines and still schedules after the state change; settlement/cancellation/expiry only remove deadlines. If alarm inspection fails, or if no alarm exists or the alarm is already due, ordinary entry performs the old bounded durable sweep as a conservative recovery path. Actual alarm delivery remains failure-propagating and enumerates durable records to expire due ownership and schedule the next deadline. This preserves cross-event deadline safety without making every high-frequency hibernation event pay O(retained streams).

The regression suite now measures reads as well as writes. With 24 retained background stream rows, a new combined legacy durable call must perform exactly one prefix list at admission. New call-ID recovery must use one point get and zero lists; terminal settlement with the already-known call view and a later duplicate terminal lookup must use zero lists. The combined production lifecycle uses three stream-row mutations through terminal acknowledgement. A synthetic pre-beta.54 call ID must show exactly one derived point miss plus one bounded migration list. Runtime-alarm tests prove that a future alarm suppresses durable deadline reads entirely and a missing alarm retains the recovery scan. Combined-admission tests separately require the active stream row and operation-deadline alarm coverage to be committed by the same transaction. Production `startEventDrivenStreamCall(createStream)` tests also prove first dispatch, identical-request resume without a second socket send, and changed-argument conflict.

Operational visibility now includes isolate-local aggregate stream-read counters (`stream_rows_read_estimate`, point gets, prefix lists, and list-returned rows) beside the existing mutation/alarm counters. These metrics never contain storage keys, stream/request IDs, OAuth/account identity, or response content. They are diagnostic estimates rather than Cloudflare billing authority; post-activation validation must compare them with Cloudflare account analytics. The accepted live runtime remains beta.50 until the owner activates a new candidate, so no reduction is claimed yet. Beta.53 never reached candidate preparation, owner activation, or acceptance and is superseded by this release-blocking beta.54 repair. Acceptance of beta.54 requires an exact candidate plus live post-activation evidence that the Cloudflare rows-read slope has materially fallen.

## 2026-08-08 beta.53 independent architecture, state-integrity, privacy, and lifecycle re-review

This review was performed independently after the beta.52 Pi/LoopX comparison and intentionally invalidated that unactivated candidate when new packaged fixes became necessary. The review re-walked architecture boundaries, dependency fan-in, persistent-state reads and deletion authorization, lock/recovery snapshots, service-provider removal, OAuth Durable Object state, browser/resource flows, public error projections, logging, subprocess settlement, test coverage, documentation claims, ignored local evidence, and dead/duplicate adapters. Beta.52 had no owner activation or acceptance record and its candidate files were deleted before beta.53 preparation.

### Findings and changes

- **Ownership evidence was not uniformly descriptor-coherent.** Process/startup locks, managed-job locks, and shared owned-JSON removal could combine a pre-open path stat with bytes from a later open. The secure-file boundary now exposes the exact BigInt descriptor stat used for identity; ownership snapshots derive content, device/inode, size, mtime, and link count from that one descriptor, reject hard links, and perform identity/single-link checks again at destructive removal. A real regression discovered during this hardening—ordinary `Stats.mtimeMs` fractional precision versus BigInt-stat integer milliseconds—was fixed rather than hidden by weakening CAS checks.
- **Corrupt-state backup had a read→rename race.** State JSON can no longer be classified as corrupt from one file and then path-renamed after replacement. `file-snapshot-preservation.mjs` creates a complete backup from the exact read bytes, removes the source only if its identity still matches, removes a misleading backup on mismatch, and preserves primary-before-cleanup error causality. Direct fault injection covers success, mismatch, source failure, cleanup-ENOENT, and AggregateError ordering.
- **Destructive control evidence had inconsistent file hardening.** Worker deletion inventory, state/recovery/root markers, internal managed-job control JSON, service ownership, and the autostart log-schema marker now use the same no-follow/lossless-identity/single-link rules appropriate to Machine Bridge-owned state. Optional project discovery and explicit user files remain deliberately less restrictive where omission or hard links cannot grant authority or justify deletion.
- **Remote/provider prose was influencing destructive continuation.** Worker deletion no longer treats `not found`-like Wrangler stderr as success. Systemd unit removal now uses a pure structured decision over definition presence, parsed active state, and disable exit status; nonzero disable cannot authorize removal of an installed definition, and a missing file does not imply an active in-memory unit is stopped. A dead generic service-result message adapter was removed.
- **Main OAuth state validation lagged the refresh-store boundary.** Schema-1 main OAuth state previously checked only that five top-level maps existed. A dedicated deep validator and shared persisted-ID contract now validate production-shaped records before authorization. Invalid-role quarantine remains separate from structural corruption. Targeted coverage is 100% functions with substantial branch coverage and the module is included in the critical coverage gate.
- **File validation and later use diverged in browser resources.** Resource permissions, size, canonical path, and injected bytes now come from one validated descriptor snapshot. CLI browser pairing likewise no longer maintains a second credential parser: only the pairing store parses/validates tokens and the CLI consumes a port-only projection.
- **Persistence-domain fan-in contained pure utilities.** `package-identity.mjs` and `state-locations.mjs` now own static package identity and pure state path/hash computation. This removed duplicate package-manifest/root parsing and reduced direct `state.mjs` fan-in from roughly 30 modules at review start to 17 while the full source graph remained acyclic.
- **Audit/log maps had prototype-key and determinism gaps.** Structured log maps use null-prototype records, and operation-risk target redaction now both retains prototype-shaped own keys and sorts object keys before hashing so semantically identical objects do not create cardinality from insertion order.
- **Error control flow contained one remaining message coupling.** `search_text` now classifies skippable files by stable `BridgeError.details.reason` rather than English error strings. Worker health also rejects unbounded or non-token version strings before they can enter status/doctor diagnostics.
- **Ignored review evidence had regrown unnecessarily.** Reconstructible external clones, 10k-file benchmark corpora, raw coverage scratch, and obsolete endpoint-bearing validation files were removed. The ignored tree fell from about 135 MiB to about 12 MiB before new final-verification scratch was generated; `.workers.dev` endpoint hits in retained ignored files fell to zero at that cleanup point.

### Explicit non-findings / decisions

- The review did **not** replace real process/service timeout tests with virtual clocks: process-tree identity and OS-provider behavior need real lifecycle coverage.
- It did **not** impose single-link policy on user-selected external plans/resources. Internal ownership state and user files have different trust semantics; over-hardening this boundary was detected during the review and corrected.
- It did **not** add a custom MCP JSON serializer. The measured extra mirror stringify cost was about 2 ms at 1 MiB and about 12 ms at 7 MiB, while the largest process results already use the dedicated `$mcpText` projection; the complexity was not justified.
- It did **not** widen near-full module line caps merely to silence architecture gates. A proposed snapshot helper temporarily pushed `exclusive-file.mjs` over its cap and was instead extracted to a cohesive 20-line domain module.
- Same-OS-user malicious replacement in the final instant between identity observation and a filesystem syscall remains an explicit residual risk; Node path APIs do not provide an atomic compare-and-unlink/rename primitive. The project now minimizes that window and fails closed on persistent ambiguity, but OS/container/VM isolation remains the boundary for a hostile peer with the same user identity.

### Verification intent

Beta.53 is not accepted by this document. The source must pass targeted regression tests, architecture/type/lint/documentation gates, the 79-task fast plan, critical coverage thresholds, the full 108-task plan, privacy/history and supply-chain checks, then `release:candidate`. The repository owner must activate that exact candidate in a real terminal before the coding agent may independently verify the live Worker/daemon and record acceptance.

## 2026-08-08 beta.52 Pi/LoopX comparative source review

Before owner activation of beta.51, the external comparison was repeated against exact upstream heads `earendil-works/pi@e47b8e37a6211ebd0b2942fa87059d64f81eec02` and `huangruiteng/loopx@29b086a1752a5329cb46de220225f2902353af3e`. Shallow local review copies were placed only under ignored `.project-local/` and their HEADs were compared with GitHub metadata. The review enumerated and line-scanned each complete text/source tree (Pi: 1,347 text files / about 314k lines; LoopX: 2,230 text files / about 807k lines), searched repository-wide concurrency/state/retry/cache/lease/output/privacy patterns, and then read the relevant implementations and tests in full. This is a source-level comparative audit, not a claim that every generated fixture or vendored/lockfile line received equal manual attention.

Pi's directly transferable mechanism was bounded concurrency around independent metadata work. Machine Bridge already had stronger write semantics than Pi's per-file mutation queue: multi-path canonical reservations, case-alias handling, flushed staging, expected-hash CAS, no-overwrite target publication, rollback, and lossless filesystem identity. It also already had analogues of Pi's stale-generation/single-flight patterns in relay generations, browser `startPromise`/generation ownership, and per-socket daemon cleanup. Pi's provider-level deferred tools are valuable inside model APIs that support `additional_tools`, but they cannot be reinterpreted as task-dependent MCP tool visibility without changing the protocol/client contract. Pi's abortable provider retries similarly do not replace Machine Bridge's existing live relay state machine; the remaining synchronous retry helper is release-only rather than an interactive hot path.

The comparison did expose two serial read fan-outs. `list_dir` could inspect up to 10,000 entries but awaited each path metadata read before starting the next. A 10,000-file benchmark measured a stable serial median near 159.7 ms versus 78.7 ms with a conservative batch width of 16; earlier cold/noisy runs showed about 2.6-2.9x improvement. `directory-metadata.mjs` now prefetches only one bounded batch with `Promise.allSettled`, consumes results in directory enumeration order, checks cancellation before scheduling and before each yield, and throws an error only when the caller actually consumes the corresponding entry. An error in a later prefetched entry therefore cannot escape after the caller has already truncated, preserving the observable serial boundary.

`search_text` had the larger read amplification: each of as many as 10,000 default / 100,000 maximum files performed secure open/fstat/read/close/UTF-8 work serially. A no-match 10,000-small-file benchmark measured about 649.4 ms serial versus 287.4 ms with ordered batch-16 reads; the initial prototype measured roughly 978.5 ms versus 287.6 ms. `workspace-search.mjs` separates scheduled files from externally visible visited files, settles a bounded batch concurrently, then consumes in original walk order. Old and new algorithms produced byte-identical results for a full no-match scan, a `max_matches=50` early stop, and a `max_files=37` stop. Tests require exact peak concurrency, ordering, limit accounting, cancellation, suppression of a later same-batch failure after an earlier match has already completed the request, and propagation of that same failure when it is actually consumed.

LoopX's strongest transferable idea was not its lease/CAS machinery—Machine Bridge's filesystem and release mutations already fail closed at stronger identity/commit boundaries—but its explicit distinction between hot read models and cold diagnostic facts. Its CLI output-budget tests also verify semantic keys and growth slopes, not only one snapshot length. Machine Bridge now applies that discipline to both compact `server_info` and the new `project_overview detail=summary`: absolute output ceilings, exact summary shape, and high-cardinality fixtures make summary size independent of exact tool membership/per-tool pending maps. A coverage expansion caught and corrected an initial projector bug where a non-record summary input could be mistaken for an empty record; the fixed projector returns full/non-record inputs unchanged and reaches 100% function / over 90% block coverage in focused measurement.

`project_overview` previously repeated exact tool membership across local tools, daemon tools, and remote authorization, retained account identity/routing fingerprints, and returned path/size for every displayed top-level entry. The summary form removes those cold fields while preserving policies and counts. Critically, remote summary is not sent below the authorization boundary: normal and legacy resumable Worker paths send an empty/default request to the daemon, apply the account-role/daemon-policy intersection, and only then project the compact result. Durable pending-call metadata stores only the validated `summary` selector in addition to the pre-existing account transform fields. Full remains the default and historical persisted records remain valid. On the owner workspace a local full projection measured about 7,484 bytes versus 2,732 bytes summary; applying the Worker owner decoration measured about 10,503 bytes full versus 3,537 bytes summary.

Several attractive external patterns were deliberately rejected. LoopX's changed-surface canary planner can return no profile for an unclassified path and would create a second dependency map beside Machine Bridge's already parallel 79-task fast gate, so it is not a release or development correctness boundary here. Pi's database writer leases are unnecessary for local locks that are never reclaimed merely because a live owner exceeded a TTL. LoopX local revision packets do not supersede no-follow descriptor reads, BigInt identity, CAS, atomic/no-overwrite publication, and rollback. Skill/context discovery was measured before considering more concurrency: warm calls were tens of milliseconds, while their large payloads are explicit cold-path instruction/skill/command content with existing omit/fingerprint controls. No second fan-out was added there.

Because the directory and search changes affect packaged runtime bytes, the prepared beta.51 tarball and manifest were deleted before any owner activation. Beta.51 has no activation or acceptance record. Beta.52 is the next eligible candidate.

## 2026-08-07 beta.51 exact-head provider correction

The first guarded push of the owner-activated and locally accepted beta.50 candidate passed package audit, dependency review, governance, workflow policy, macOS platform/install, Ubuntu full, and CodeQL Actions checks, but exact-head provider evidence exposed two independent blockers. Beta.51 makes only the fixture portable by deriving the root/outside paths with `path.resolve()` and the expected job directory with `path.join()`. The production managed-job directory resolver and its lossless identity checks are unchanged.

Because the CodeQL repair changes packaged production source, beta.50 cannot be published despite successful owner activation and local acceptance. ## 2026-08-07 beta.50 independent adversarial re-review

Beta.49 was not activated. A second independent pass treated the prepared beta.49 candidate as untrusted and reconstructed architecture, file-transaction semantics, stream admission, cleanup causality, filesystem identity, logging fields, ignored-local retention, tests, package boundaries, and release documentation from source. That review found a release-blocking patch-transaction defect: the beta.49 mutation coordinator used one case-insensitive resolved-path identity on macOS/Windows, but patch collision preflight case-folded only Windows and the patch transaction used overwrite-capable rename for staged targets. On a case-insensitive macOS volume, distinct patch strings such as `Foo` and `foo` can denote one directory entry; a single multi-file patch could therefore pass preflight and let a later staged target replace an earlier one. The beta.49 private candidate was deleted before any owner activation.

Beta.50 makes conflict identity a shared primitive and changes staged patch target publication to no-overwrite hard links. `EEXIST` after preflight becomes `conflict/target_appeared`; the transaction never treats a late alias as permission to overwrite. Transaction mechanics now live in `workspace-file-transaction.mjs`, separate from `WorkspaceFileService` authorization/path/content orchestration. Whole-file and patch staging failures aggregate the primary failure with cleanup failures without exposing private paths or content. Once a create-only target has actually committed, a later staging unlink failure is reported as a fixed warning rather than converting a completed side effect into a false failure. Patch rollback preserves the primary commit error followed by every rollback/artifact cleanup cause.

The same cleanup audit found an unused but unsafe branch in the shared synchronous exclusive-file helper. Its former `cleanupTargetOnFailure` option unlinked the target whenever the exclusive hard-link step failed before `linked=true`; on `EEXIST`, that target belongs to the pre-existing winner and must never be removed. No production caller used the option, but beta.50 removes the behavior and adds a regression that supplies the old flag and requires the existing target to survive. Pre-commit descriptor/staging cleanup failures now aggregate with the primary error. Post-commit staging cleanup remains a successful commit with fixed warning metadata and non-enumerable internal cleanup evidence. Worker-secret setup consumes that evidence immediately, performs one identity-checked second deletion attempt, and refuses to invoke Wrangler if a secret-bearing hidden staging file cannot be proven removed.

A portability sweep generalized the beta.47 Windows finding. `secure-file.mjs` previously converted `dev` and `ino` to Number and, if either value was not a safe integer, returned `true` from its identity comparator. That was an explicit fail-open path at a primitive used by Worker fingerprinting, owner state, service configuration, pairing, operation authorization, hardened toolchains, security audit, and other sensitive reads. Beta.50 introduces a shared lossless filesystem-identity boundary. Default descriptor/path identity observations use BigInt `fstat`/`lstat`; safe injected Numbers remain supported, while unsafe Numbers fail closed. Process/startup locks, managed-job locks/directories, exclusive owner-file removal, Worker-secret cleanup, audit caching, and SSH-key snapshots use the same exact device/inode representation. Fault injection uses adjacent inode values `2^53` and `2^53+1`, which collapse under IEEE-754 Number, and requires them to remain distinct.

The Worker review found over-wide coordination rather than a missing lock. Legacy `McpStreamChannel` serialized every stream subscription through one Promise and held that queue across the post-registration storage read, even though subscription capacity is per stream and the count-to-`acceptWebSocket` step contains no await. Beta.50 removes the global queue. A deterministic test blocks stream A's second storage read while stream B must finish subscription, preserving the required storage-recheck race defense without unrelated-stream head-of-line blocking.

Logging and local-retention privacy were reviewed independently of publication scanning. Unexpected Worker HTTP failures now log only a low-cardinality route class, not request path text. Routine Worker deployment logs no longer retain Worker name or endpoint; the explicit operator handoff remains unchanged. The ignored `.project-local` tree contained no detected AWS/GitHub/npm/JWT token shapes, but it had accumulated reconstructible toolchain experiments, old live-endpoint probes, and machine paths. Removing only artifacts with no tracked dependency reduced it from about 406 MiB to 12 MiB and eliminated remaining `workers.dev` endpoint matches. Ignored storage remains machine-private operational state, not an exemption from retention/privacy discipline.

A second fail-open search distinguished malformed metadata from storage failure. Startup/daemon process-lock reads, managed-job recovery/transition locks, owner-state locks, and `runner.pid` formerly had catch paths that could collapse a bounded-read or storage error into malformed/null/fallback owner state. In the destructive cases, sufficiently old oversized metadata could then become reclaimable even though Machine Bridge had never reliably read the owner. Beta.50 separates the phases: ENOENT is absence, a successful bounded read followed by malformed UTF-8/JSON is content corruption with the existing bounded policy, and size/permission/I/O/descriptor/identity failures propagate. Recovery/pruning already retain unreadable managed-job state, so removing the deep fallback makes the existing fail-closed outer behavior effective. Oversized lock/runner fixtures verify the existing files survive.

The same pattern existed in autostart log rotation. `readLogSchema()` previously converted every exception to an empty string; `trimAutostartLogs()` interpreted that as a schema mismatch and truncated both daemon logs before rewriting the marker. An unreadable or oversized schema marker could therefore erase the very evidence needed to diagnose the storage failure. Beta.50 treats only ENOENT as first-run absence. A readable old marker still performs the intentional schema reset; any bounded-read, path-safety, permission, or I/O error stops before opening/truncating the log streams. The regression uses an oversized marker and requires both daemon logs and the marker to remain unchanged.

The source import graph remained acyclic. Near-ceiling modules were reviewed individually rather than split for line-count aesthetics: state-machine-heavy OAuth, daemon-socket, and diagnostic modules remain intact where extraction would scatter invariants. Same-OS-user malicious filesystem replacement remains an explicit residual risk outside the Node process's sandbox guarantees; mutually untrusted users still require OS/container/VM isolation. Beta.50 requires a new exact candidate and owner activation after the final frozen-source gates; no beta.49 activation or acceptance evidence exists.

## 2026-08-07 beta.49 comparative runtime review

A read-only comparative review of two actively maintained agent/control-plane projects was used as an adversarial design check rather than as a source-code dependency. LoopX's strongest transferable idea was the separation of canonical decisions from compact hot-path projections and explicit write-intent/conflict semantics. Pi's strongest directly applicable implementation pattern was per-canonical-file mutation coordination, including the requirement that cancellation not release a queue while an underlying filesystem operation is still in flight. Machine Bridge already had stronger local commit primitives than either pattern required: SHA-256 preconditions, no-follow and hard-link defenses, flushed staging files, atomic link/rename, and rollback-capable multi-file patches. The review therefore did not replace those primitives or adopt another agent runtime.

The concrete beta.49 defect was narrower: `LocalRuntime` serialized every `write_file`, `edit_file`, and `apply_patch` behind one process-wide Promise even when the operations touched disjoint files. The new `file-mutation-coordinator.mjs` accepts already-resolved absolute paths, normalizes case on Windows/macOS for conservative alias safety, registers all unique paths of a transaction before awaiting any predecessor, then releases them only after the callback settles. `WorkspaceFileService` resolves a single write/edit target before reservation and resolves all patch sources/destinations before reserving the complete set; mutable file contents, target existence, hashes, and patch hunks are re-read/evaluated only inside the reservation. Same-file concurrent edits therefore observe fresh state, multi-path patches block overlapping single-file mutations, and unrelated files can proceed independently.

Direct tests cover same-path ordering, independent-path concurrency, overlapping multi-path reservations, duplicate-path deduplication, callback failure cleanup, and real concurrent edits through `LocalRuntime`. Architecture checks prevent the global runtime queue from returning and require registration-before-wait/settlement semantics; critical coverage gates the coordinator independently. The same comparative review found a separate context-amplification issue: authenticated `server_info` always returned its full authority/tool/OAuth/observability graph even when an agent only needed version/readiness/relay health. Beta.49 therefore adds an explicit `summary` projection while preserving `full` as the default. Summary is a post-decision projection, not a separate authorization computation; it intentionally omits raw account ID, OAuth metadata, exact effective/advertised tool arrays, per-tool Worker observability, and local security/trust detail. Tests require materially smaller local and remote fixtures and preserve the detail argument through both ordinary and legacy resumable MCP paths. The final projection review also moved daemon ready-socket status formatting out of `BridgeRoom` into a pure `daemon-status.ts` module; stale-socket reclamation remains in the Durable Object, while connected/disconnected status shape and readiness/liveness constants are tested independently. This reduces the Worker composition root from 843 to 820 lines and tightens its enforced ceiling to 830. A third interruption audit found that `ToolExecutor` checked cancellation again after the handler returned even though its inner observability/audit middleware had already committed a completed outcome. For a filesystem or process operation whose final await had crossed a non-cancellable commit boundary, that could expose `cancelled` to the caller after the side effect actually completed. Beta.49 removes only that retroactive veto: pre-handler cancellation and every manager/service cancellation checkpoint remain, remote cancelled owners still suppress terminal delivery, and the local handler result becomes the single settlement fact once it returns. A targeted regression cancels while a synthetic commit is in flight and requires successful completion, one completed metric, zero cancelled/failed metrics, and no registry leak. No credential, account, network, host-UI, release-activation, or authorization boundary changes. The LoopX lock comparison also exposed a local cleanup-causality gap: `withOwnerStateLock` previously threw a release/ownership error before rethrowing an already-captured callback failure, so a secondary cleanup fault could erase the primary state-operation cause. Beta.49 now aggregates primary and release errors in that order; a fault-injection regression corrupts the owned lock during a failing callback and requires both causes to survive.

The Pi supply-chain comparison confirmed two repository defaults worth evaluating separately. Machine Bridge already rejects non-exact root dependency ranges in its release architecture contract, so adding `save-exact=true` simply makes ordinary future npm save behavior agree with that invariant. Pi also uses `min-release-age=2`; Machine Bridge intentionally does not adopt that setting. npm 12 defines it as a tree-resolution filter that makes versions published inside the age window ineligible and documents that it may block `npm audit fix` from installing a newly published patched version. This project instead relies on explicit exact upgrades, committed lockfiles, hardened npm, zero-vulnerability audits, registry signatures/attestations, lifecycle-script allowlists, private toolchain verification, and isolated consumer-package installation. A blanket age filter would reduce emergency patch agility without adding equivalent evidence about a version that has aged past the threshold.

Beta.48 acceptance remains evidence only for the immutable beta.48 artifact. Beta.49 was later blocked before activation by the beta.50 independent review above and must not be activated or accepted.

## 2026-08-07 performance, stability, architecture, and privacy re-review

A separate review after the beta.47 Windows/process remediation reconstructed the slow-path and interruption mechanisms instead of treating individual timeout symptoms as transport failures. The original fast plan ran 79 gates serially and took 53.4 seconds in the review environment, leaving almost no margin below the remote 60-second foreground execution ceiling. The runner now preserves every gate while directly executing simple single-Node scripts, retaining npm for lifecycle/compound/non-Node scripts, and using bounded concurrency with explicit process-heavy serial barriers. The syntax gate was independently responsible for hundreds of process launches; it now parses the dynamically discovered JavaScript surface in one non-evaluating VM-module parser subprocess plus the existing shell-wrapper check. The final local fast-plan measurement after these changes was 17.8 seconds, about one third of the original wall time; elapsed time is diagnostic evidence rather than a release guarantee on other hardware. The release-level review also found wall-clock-only fault-injection delays: the direct managed-job suite spent 189.2 seconds waiting for a deliberately long descendant timeout even though the assertion concerns the timeout/termination state transition, not the absolute duration. The same real process-tree fixture now uses a 15-second deadline and completed locally in 23.9 seconds while retaining the ignore-SIGTERM descendant and terminal-state checks. The shell process-tree fixture remains real but uses a ten-second timeout. Coverage no longer launches `runtime-self-test.mjs` separately after `local-self-test.mjs`, because the latter already invokes `runtimeSelfTest`; this removes duplicate execution without removing a covered path.

The same review reduced request/context amplification. `project_overview` now runs independent inventory/Git-root probes concurrently and returns at most 40 top-level entries with total/truncation metadata. Server and bootstrap guidance no longer requires `resolve_task_capabilities` before straightforward direct file, Git, or shell work; the resolver remains the explicit refresh/routing path for project instructions, skills/commands, and application/browser tasks. Documentation now distinguishes modern static `server/discover` from the legacy initialization-time bootstrap path.

Relay architecture was re-reviewed rather than only retested. Its maximum execution budget plus the five-second Worker overhead allowed a terminal deadline of 90 seconds, leaving no credible allowance for request admission, Durable Object work, public SSE forwarding, host processing, or final assistant-message submission. The exact host deadline is external and not a Machine Bridge contract, so beta.31 does not claim a mathematically guaranteed bound. It conservatively caps remote synchronous execution at 60 seconds, records the Worker settlement deadline five seconds later, and directs longer work to durable process sessions or managed jobs. Admission and transport latency can consume part of that interval.

A second source review found that the first beta.31 candidate did not actually preserve that split. `daemonToolTimeoutMs` returned the execution budget plus overhead, and the Worker reused the same value both for its pending-call deadline and for the daemon `tool_call.timeout_ms`. Tools whose handler had no narrower inner timeout could therefore execute for the entire 65 seconds and consume the intended settlement margin. Beta.31 now computes an explicit `{executionTimeoutMs, settlementTimeoutMs}` budget: the daemon receives 60 seconds at most, while the Worker deadline is recorded at 65 seconds from Worker registration. Tests assert the two values independently for transient and durable stream paths, including the one-second integration timeout case.

The same review found a discovery-cache mismatch outside the current repository source: the live beta.30 Worker and canonical catalog enforced an 85-second maximum, while the tool schema supplied to the active ChatGPT conversation still advertised 600 seconds. A 120-second request was consequently generated by the host and rejected before dispatch. Beta.31 publishes a 60-second canonical schema and documents that an already-open host may need rediscovery or reconnection; the Worker remains the authoritative validation boundary. Because Machine Bridge cannot invalidate a host-owned schema cache, it must continue failing oversized requests with `side_effects_started=false`.

The same second review rejected the first observability fix as semantically ambiguous. A terminal publication with zero live internal subscribers can be normal: completion may precede subscription, after which the outer Worker obtains the persisted result through a storage-backed HTTP response. Conversely, a successful internal WebSocket send proves only Durable Object-to-outer-Worker queueing, not public SSE consumption or host receipt. Beta.31 therefore exposes separate aggregate counters for terminal publications, live internal-subscriber sends, storage responses, and storage-race sends/failures. `server_info.tool_delivery` explicitly states that host terminal receipt is not observable and that these counters cover legacy resumable Worker-internal storage and subscription transport only. Request identity, tool arguments, command text, and result content remain absent.

The resumption configuration retained another stale dependency on the former local 610-second relay envelope. A stream created during legacy prepare but never activated could remain for 730 seconds, consuming one of 64 bounded stream slots, even though hosted settlement now ends by 65 seconds. New unactivated records are capped at 185 seconds: maximum hosted settlement plus the 120-second replay window. Once activated, the existing operation/reconnect expiry algebra remains authoritative and extends the record as required.

## 2026-08-02 version 3.0.0-beta.30 interruption and recovery review

A repeated-call incident was reproduced while the local launchd daemon remained the same healthy beta.29 process. Recent security-audit records showed that many 20–78 second local calls reached terminal state even when the MCP host reported interruption, and the public MCP endpoint was briefly unreachable while the daemon connection identity remained unchanged. Live Cloudflare sampling after recovery showed no Worker exceptions; internal legacy subscription WebSockets closed frequently as part of their ordinary terminal lifecycle. The evidence therefore separates three cases: local execution failure, Worker/DO delivery interruption after admission, and a connection failure before Worker code runs. Only the first two are observable or repairable inside this repository; a pre-Worker edge/TCP/TLS failure still requires host retry or an independently operated alternate endpoint.

The review found five concrete amplification defects. The shared tool catalog advertised 120-second defaults and a 600-second maximum while the Worker rejected values above 85 seconds, allowing the host to generate requests that could never pass remote validation. After the catalog was corrected, the full gate exposed the inverse execution mismatch: `exec_command` and `run_process` still defaulted to 120 seconds locally when relay arguments omitted the field, and `run_local_command` could inherit a 600-second owner manifest even though the Worker waited only 60 or 85 seconds. A lost prepare response caused the outer Worker to repeat no request, while a client retry had no explicit argument fingerprint for safe in-flight reattachment. Finally, the stateful burst limiter keyed only by Worker hostname, so every account and client shared one 120-request/minute bucket.

Different retry IDs, malformed IDs, missing nonce state, and ordinary client replay fail closed.

The burst guard is now layered: a 1,200-request/minute route/Worker bucket limits aggregate abuse, while a 120-request/minute route/subject bucket isolates authenticated credentials or an anonymous network identity through a truncated SHA-256 digest. ## 2026-08-01 version 3.0.0-beta.29 security-audit storage review

Review of the live 4,096-event audit chain found that moving persistence to a worker thread removed daemon event-loop blocking but did not remove storage amplification. Each sparse batch still read roughly 3 MiB, parsed the complete document, recalculated every SHA-256 link, serialized the complete state, atomically replaced it, and called `fsync`. On the inspected machine, a cold full-chain verification took approximately 1.3 seconds. The previous implementation therefore could accumulate audit work at ordinary interactive call rates even though tool-result delivery itself remained asynchronous.

Beta.29 gives each audit worker a verified storage session. The first access performs the complete bounded read and chain verification. Subsequent writes reuse that state only while the on-disk regular-file identity, size, modification time, and metadata-change time remain unchanged. A cross-process writer or external alteration changes that identity and forces a fresh secure read and full hash-chain verification under the owner-state lock. The cache never turns an unverifiable file into an accepted state, and a failed write does not advance the cached state. In the same environment, cached single-record writes fell to roughly 39–264 milliseconds; the remaining cost is full-file serialization, atomic replacement, and `fsync`, not repeated chain verification. A segmented append/checkpoint format remains a possible future optimization if sustained high-rate audit throughput becomes a product requirement.

The review also proved that the former retention contract was internally inconsistent. Every event field could be within its legal bound while 4,096 events exceeded the separate 4 MiB file ceiling. The storage layer then rejected the write and left the audit backend unhealthy before reaching its advertised count limit. Retention is now the intersection of the event and byte limits: event encodings are measured exactly, the oldest prefix is removed until both bounds hold, and the anchor advances to the last removed hash so the retained suffix verifies independently. Diagnostics expose `maximum_bytes` alongside the event maximum.

Faster writes exposed a pre-existing lock race. After exclusive creation failed with `EEXIST`, a holder could release the lock before the contender read it. The contender treated both `ENOENT` and malformed content as corruption. The lock reader now returns distinct missing, invalid, and valid-owner states; only missing retries, while malformed state continues to fail closed. Cross-worker audit tests exercise this release/acquire window and verify continuous sequence numbers with no lost events.

The live review also showed isolate-local event counters that could appear inconsistent with the persistent pending-call snapshot after an isolate restart. That is not durable-call loss: a persisted call may start in one isolate and complete in a later isolate. Beta.29 adds an explicit machine-readable `metric_scope` declaring the current-isolate lifetime and non-closed counter algebra; the persistent pending-call snapshot remains authoritative for active ownership.

This source review does not activate beta.29, replace the running beta.28 daemon, deploy the Worker, modify live audit or legacy authorization files, publish npm, create a tag, or record acceptance.

## 2026-07-21 version 2.0.0 remote-authority audit

The critical question was whether canonical `full` could retain its automation value without allowing one long-lived remote bearer to remain equivalent to unattended local-user control. Neither form changes the persisted profile nor can be remotely extended. Pending records retain only bounded metadata and a target digest, not command text or user content.

The daemon transport now uses an enrolled P-256 identity. An initial challenge-only design was rejected during review because unauthenticated network clients could still create and replace candidate sockets until challenge failure, producing an availability attack. The final protocol requires a signed preflight before WebSocket upgrade and a second Worker challenge before tool advertisement. Signed preflight nonces are consumed once through bounded Durable Object transaction state, closing the short replay window without requiring fragile sub-minute clock synchronization. Only the public JWK is deployed. The private JWK remains in owner-only local state. The readiness probe and verified-incumbent handover remain independent requirements.

Reusing a consumed token revokes all access and refresh records in that family. Because merely changing the daemon protocol would not invalidate an already issued thirty-day access token, first device enrollment also rotates the deployment-wide token version. This deliberately requires every pre-2.0 client to authorize again while ordinary subsequent startup preserves credentials.

Account administration keeps the local operator workflow but no longer transmits the administration key as a bearer. Each request signs Worker origin, method, path, body SHA-256, timestamp, and random nonce with HMAC-SHA-256. The Worker validates the body against the signed hash and consumes the nonce once through the same bounded transactional nonce component used by daemon preflight. A repeated request is rejected, and malformed nonce state fails closed rather than being silently reset.

Risk classification, lock ownership, and lease persistence remain separate modules, and persisted lease/pending records are validated field by field before participating in authorization.

Large object results have one authoritative `structuredContent` value and a short shared text projection rather than a second full JSON serialization. UTF-8 head/tail previews no longer split Chinese or emoji code points. Complete and production dependency audits remain at zero vulnerabilities; registry signatures, attestations, package file modes, generated references, and reachable Git history privacy checks are independently verified.

## 2026-07-20 version 1.2.10 transient-relay recovery audit

Repeated ChatGPT web executions were terminating even though the local daemon and Worker were healthy immediately afterward. The causal defect was not the tool implementation or its configured timeout. A brief WebSocket loss—made more likely when the daemon relay traverses an environment-selected local proxy—was promoted into a terminal request failure at both ends: the Worker rejected every pending call assigned to the closed socket, while the local runtime cancelled all relay-origin calls and killed their ordinary child processes. Automatic WebSocket reconnection restored future traffic but could not recover the request already abandoned by both state machines.

The correction introduces a bounded continuation identity rather than weakening cancellation globally. Every local daemon process creates one random ephemeral `instance_id` and presents it in the current-version hello. On socket loss, the Worker detaches only calls owned by that socket and retains their OAuth/session request indexes for thirty seconds. A replacement socket may rebind them only after presenting the same process identifier and completing the existing end-to-end readiness probe. The local runtime mirrors this interval: active calls continue, completed result envelopes are retained in memory, and readiness triggers replay. A different process instance cannot claim the pending IDs; daemon restart remains terminal rather than pretending to provide durable execution.

The recovery path remains bounded and fail closed. Explicit MCP cancellation and HTTP client abandonment still remove the remote receiver immediately. A connected daemon receives cancellation as before. If cancellation occurs while disconnected, the next same-instance handshake carries an authoritative `resume_calls` set before `ready_ack`; the local runtime cancels any active or completed call absent from that set, so a fast reconnect cannot revive a request whose HTTP receiver disappeared. Timeout remains authoritative. At thirty seconds without same-instance readiness, the Worker rejects detached requests and the runtime cancels calls, discards queued results, and enters the existing persistent-outage reporting path. No tool arguments, commands, paths, outputs, proxy endpoint, or result content are added to logs or durable storage.

Regression evidence covers three layers: deterministic pending-registry detach/rebind/expiry tests; local runtime queue/replay, resumed-call reconciliation, cancellation, and grace behavior; and real workerd OAuth/MCP/WebSocket fault injection that both completes a detached request after same-instance reconnect and proves a request cancelled while detached is excluded from the next `resume_calls` set. Malformed or missing daemon-instance identifiers are rejected as protocol errors. The version remains a current-only Worker/daemon protocol unit and requires normal candidate convergence before live use.

## 2026-07-17 version 1.2.7 process-supervision and lifecycle audit

The core question in this review was not whether the existing green suite covered many paths; it was whether failure and ownership boundaries remained truthful when processes resist termination, startup is interrupted, proxy state is hostile, or the operating system refuses a spawn. The audit found that generic argv validation and process-tree termination had drifted into the interactive-session module, while shell and managed-job paths maintained adjacent termination branches. # Engineering and security audit

## 2026-07-17 version 1.2.5 end-to-end relay-readiness audit

The incident sequence disproved the previous meaning of “connected.” Version 1.2.3 correctly stopped treating every hibernation-restored `OPEN` WebSocket as live, and version 1.2.4 restored the missing local relay-session generation. Those changes repaired two concrete defects, but the startup contract still established readiness from `hello_ack` and heartbeat traffic. Both signals exercise transport authentication and one-way control messages; neither proves that an inbound request can traverse the local dispatcher and return on the same authenticated relay generation. A regression in that return path could therefore keep heartbeats healthy while every user tool timed out.

Version 1.2.5 replaces that proxy signal with direct evidence. After `hello`, the Worker stores the socket as `probing`, returns `hello_ack`, and sends a random `relay_probe`. The local runtime validates the probe and returns `relay_probe_result` through `deliverRelayToolResult` and `sendForSession`, using the exact session-generation boundary that protects real tool results. Only then does the Worker promote the socket to `daemon`, send `ready_ack`, advertise tools, and allow the local startup promise to resolve. The local side independently records successful probe-result delivery; it rejects `ready_ack` before that evidence and rejects any ordinary `tool_call` while the relay is authenticated but not ready. The probe identifier is random, bounded, short-lived attachment metadata; it contains no tool arguments, paths, commands, output, account data, or credentials.

Replacement is now fail-safe rather than eager. The current verified daemon remains authoritative while a candidate authenticates and completes the probe. Malformed or mismatched results close the candidate with a protocol error; missing results reach an independent readiness deadline; neither path rejects calls assigned to the incumbent or changes its advertised policy. Only a verified candidate closes the old socket. Durable Object alarms independently enforce candidate hello, probing readiness, and steady-state liveness deadlines across hibernation. `server_info` distinguishes current authenticated, probing, and ready socket counts and reports `readiness_verified`; control-plane consumers no longer need to infer service health from cumulative socket counters.

The review also found a lower-severity routing defect in the user's pending skill rename. The ranking algorithm gave short generic identity words such as `web` the same strong weight as a distinctive capability name, so unrelated browser work could cross the selection threshold. Removing only that weight exposed a hidden dependence on the same generic token for Chinese research requests. The correction suppresses strong identity credit for generic words and adds an explicit Chinese research/search semantic mapping. Positive and negative regressions now encode both sides of the decision boundary.

Architecture review extracted daemon attachment mutation from the Worker composition root into `DaemonSocketRegistry`, added an independent line cap and responsibility assertions, removed a duplicate HTTP method guard, and made inbound liveness updates await alarm rescheduling rather than leaving an unobserved promise. Fault injection covers no-ready-ack reconnect, invalid replacement probes, incumbent preservation, verified handover, session-bound probe return, and current observability. The complete package gate, Worker dry run, dependency/signature/privacy checks, and cross-platform CI remain the release boundary. This source change does not deploy the Worker, replace the running daemon, rotate credentials, publish npm, create a tag, or create a GitHub Release; a live installation remains on its old behavior until Worker, daemon, and extension converge on 1.2.5.

## 2026-07-17 version 1.2.2 relay-lifecycle and logging audit

The reported warning was the visible symptom of a call-lifecycle mismatch rather than a failed local tool. The Worker could remove a pending call after MCP cancellation, timeout, daemon disconnect, or client abandonment, while the local runtime still completed its asynchronous operation and entered one unconditional result-delivery path. When the original WebSocket had closed, the daemon emitted one `relay.tool_result.delivery_failed` warning per late completion. More seriously, if a replacement relay had already authenticated, the old result could be written to the new socket; the Worker rejected it because its pending record was socket-bound, but the local transport did not enforce the symmetric session boundary.

The correction gives each authenticated local relay connection a monotonically increasing in-memory generation and captures that generation with every incoming call. A result may be sent only through the generation that delivered the call. Explicit cancellation and relay disconnect also mark the eventual local result for disposal. Expected cancellation/disconnect/reconnect races are therefore debug-only `relay.tool_result.discarded` events, while a synchronous send failure on the still-current socket continues to invalidate the ambiguous transport and enter the ordinary outage state machine.

A second defect existed one layer earlier. The Worker already handled MCP `notifications/cancelled`, but an HTTP client that disconnected without sending that notification could leave the pending internal ID and session request-key index until the tool timeout. The pending-call registry now owns AbortSignal registration and cleanup atomically with its timer and indexes. The Worker deployment explicitly enables Cloudflare `enable_request_signal` and `request_signal_passthrough`, which are both required because the public Worker forwards the request into a named Durable Object. A deterministic registry test covers active and already-aborted requests; the complete local workerd suite continues to cover OAuth, explicit MCP cancellation, WebSocket routing, timeout, and socket loss.

Logging was reviewed as a user interface rather than a serialization dump. Human mode now uses the supplied natural-language explanation and omits the redundant stable event identifier; newline-delimited JSON retains that identifier for ingestion. Tool starts, outcomes, cancellation, timing, and late-result disposal remain debug-only. Worker observability adds an `unmatched_results` counter for a result that arrives after its pending record has been removed, preserving anomaly evidence without storing tool arguments, command text, paths, or result content.

The PR security gate also classified the generated account credential verifier as `js/insufficient-password-hash`. The account credential contract forbids human-chosen passwords and generates 256 random bits; the Worker validates the exact generated-token format and stores a verifier using an independent 128-bit salt plus HMAC-SHA-256. This does not have the low-entropy offline-guessing risk modeled by the rule. The exact rule/path pair is therefore explicitly accepted through 2026-10-21, when the project must re-evaluate CodeQL behavior or adopt a portable slow KDF. The exception is fail-closed, path-specific, expiring, and covered by the architecture inventory.

The broader pass rechecked architecture boundaries, cancellation and reconnect branches, release/configuration contracts, privacy redaction, package version convergence, TypeScript and checked-JavaScript contracts, lint, Worker integration, and documentation drift. An additional deployment defect was found during fault reproduction: request cancellation support was implemented in code but the required Cloudflare compatibility flags were absent, so the signal could not reach the Durable Object in production. Architecture tests now make both flags non-optional. Version 1.2.2 retains local state schema 6 and policy revision 5; normal startup must converge the Worker and daemon versions, and the unpacked browser extension must be reloaded. ## High-impact findings and corrections

### Lock and process identity

Process locks were previously created directly at their final path and then populated. A competitor could observe an empty or partial JSON file. Locks also relied primarily on PID liveness, which cannot distinguish PID reuse.

The runtime now:

- writes and `fsync`s a private temporary file before atomically claiming a lock with a same-directory hard link;
- records a random ownership token and process start time;
- validates PID liveness, process start time, lock age, purpose, workspace, and file identity;
- removes a stale lock only when its device, inode, size, modification time, and token still match the inspected snapshot;
- gives a recent malformed lock a grace period rather than deleting a possibly in-progress claim;
- waits a bounded interval for ordinary startup/state operations instead of failing immediately.

Managed-job transition, recovery, and runner identity follow the same ownership and process-start-time rules. Numeric-only runner records are rejected.

### Service lifecycle

Service providers returned inconsistent result shapes, and removal could continue after an incomplete stop. Full uninstall considered too little profile state.

The lifecycle is now fail-closed and ordered:

1. stop the platform service;
2. stop every verified workspace daemon in scope;
3. confirm each stop result;
4. remove the service definition only after all stops succeed;
5. retain service definitions and state when any phase fails.

macOS, systemd, and Windows Scheduled Tasks now return a common `ok` contract. Full uninstall scans all known profiles and can recover workspace identity from daemon locks when a state file is unavailable.

### State persistence and deletion

State reads previously classified any read error as corrupt JSON and could continue with an empty state. A dangerously selected state root could also overlap a workspace.

The runtime now:

- backs up a file only after it was read successfully and its JSON content is actually invalid;
- propagates permission, type, symbolic-link, size, encoding, and I/O failures;
- uses one shared `fsync` plus atomic-replacement primitive for state, job, runner, browser-pairing, and service-definition writes;
- rejects a state root that overlaps the selected workspace in either direction before creating state;
- acquires a state-root maintenance lock to block new profile/state operations and state-backed operations from already constructed managed-job/browser managers, and cross-checks deletion against global workspace selection, profile state, daemon locks, state markers, and known directory shape;
- treats unreadable process locks as an uninstall blocker rather than evidence of inactivity.

### Process-tree cleanup

CLI helper commands and managed jobs could terminate the direct child while leaving descendants alive. Escalation timers could be cleared or unreferenced before killing a resistant descendant.

Timeout and cancellation now target the process group/tree, keep the escalation timer alive, and issue a bounded `SIGKILL`/Windows tree termination after graceful shutdown. Tests use descendants that deliberately ignore `SIGTERM`.

### Privacy and logging

The privacy gate did not inspect tracked npm authentication configuration or several common credential formats. Free-form log sanitization had corresponding gaps.

Checks and redaction now cover:

- generic, encrypted, OpenSSH, RSA, EC, and DSA private-key headers;
- npm, GitHub, GitLab, Slack, Google API, AWS, live payment, and common API-secret formats;
- JWT-shaped bearer values and URLs with embedded credentials;
- non-example email addresses and absolute user-home paths;
- credential-shaped publication filenames;
- authentication, identity, environment interpolation, and credential URLs in a tracked `.npmrc`.

Findings report only file, line, and rule. The matched value is never printed. A tracked `.npmrc` remains permitted for non-secret repository settings such as `engine-strict=true`.

### Local automation boundaries

Browser upload metadata now requires a safe single-component filename and canonical MIME type. Derived local filenames have controls and separators removed. Application action text rejects NUL bytes. Sensitive browser and Accessibility values remain excluded from results.

Restricted filesystem reads now add `O_NOFOLLOW` for the final path component in addition to canonical workspace containment.

### Test and release integrity

The hand-maintained syntax file list was replaced by a recursive scanner. Package scripts are checked for missing entrypoints, release helper scripts are packaged, npm package modes are validated, and installation guidance is checked across the CLI and documentation. Dedicated tests cover lock concurrency, atomic replacement, PID reuse, malformed locks, service removal ordering, process-tree termination, state read failures, unsafe state roots, browser upload metadata, and expanded privacy patterns.

## Reviewed areas without material code changes

The review also rechecked Worker OAuth/PKCE validation, exact redirect/resource binding, token hashing/version revocation, registration and failure limits, Durable Object serialization, daemon WebSocket authentication/replacement, CSP/no-store response headers, static MCP catalog parity, browser loopback Host/Origin/subprotocol validation, and fixed-code JXA/browser execution. Existing controls and integration coverage were retained.

## Residual limits

No review can prove the absence of all defects. Important residual boundaries are:

- Node.js cannot provide a portable `openat`-style directory capability for every filesystem operation. Canonical containment plus `O_NOFOLLOW` protects the final component, but hostile same-user code can still race parent-directory replacement. Use a dedicated low-privilege account, VM, or container for untrusted repositories.
- Same-user malicious processes can inspect memory, signal processes, alter browser profiles, or manipulate files the user can access. Machine Bridge is not an OS sandbox.
- Hard-link atomic lock claims require a local filesystem that supports same-directory hard links. Failure is explicit; the runtime does not fall back to a partial-write-prone lock.
- Service-manager behavior varies by OS version and local policy. Provider failures remain visible and fail closed, but operator intervention can still be required.
- Browser pages, application UIs, project instructions, skills, command manifests, and command output are untrusted content. Human/host approval remains necessary for consequential actions.
- The MCP host may filter tools, omit server instructions, or block calls before they reach Machine Bridge; the server cannot observe or override that boundary.

## Ongoing review rule

A future change to locks, state deletion, service lifecycle, detached processes, credentials, browser/app authority, package contents, or public transport must add a behavior-level regression test and update the applicable security/operations documentation. String-presence tests may supplement, but must not replace, executable state-transition tests.

The causal mechanism was a global `mcp-stream-index` row rewritten alongside every per-stream transition. Beta.45 makes per-stream records the sole authority, deletes the legacy index once, meters only committed mutations, and enforces three-row immediate and four-row daemon lifecycle ceilings. The beta.44 acceptance is invalid because the quota repair changes Worker and package bytes; only a newly activated and observed beta.45 candidate may be accepted.

### 2026-08-07 beta.45 external CI gate incident

The accepted beta.45 commit passed the exact local 108-task full plan, package/install/SBOM/privacy checks, live Worker and daemon verification, and guarded push. Its first pull-request run nevertheless supplied two independent external counterexamples. On Windows, Git checkout materialized workflow YAML with CRLF because the repository had no workflow-specific `eol=lf` attribute; `workflow-policy:test` correctly rejected the changed bytes. In CodeQL 2.26.2, seven release error sinks were classified as log injection because a sanitized but externally derived diagnostic was interpolated into a log string, and the macOS trust-broker tamper regression was classified as a filesystem race because it reopened a path after the builder had inspected it. These findings are not accepted as exceptions.

Beta.46 preserves the strict LF-only workflow policy and fixes checkout instead, emits release failures as bounded JSON records after portable redaction, and mutates the test binary through a no-follow validated descriptor. The beta.45 acceptance is invalidated because release scripts are packaged. Local simulation can prove Git attribute resolution, single-line JSON encoding, no-follow descriptor behavior, and project regressions; only the subsequent GitHub Windows and CodeQL runs can close the platform/environment oracle.
