# Testing strategy

The project treats transport, authorization, local authority, and state removal as separate failure domains.

## Required suites

The resource profile suite also pins the live-release exception discovered under multi-project contention and tightened after both npm `script-shell` and mutable-checkout review. Only exact direct Node argv `node <activated-runtime-package>/scripts/release-oauth-canary.mjs --allow-live-oauth-canary` may receive the `release-control` light profile. The script operand must be absolute and canonicalize to the running package's own canary; `node scripts/release-oauth-canary.mjs ...`, copied workspace canaries, npm/pnpm lifecycle invocation, shell wrappers, missing/extra argv, and lookalike entrypoints never receive release-control identity. Production admission also requires the resolved Node executable to canonicalize to the daemon's own `process.execPath`, startup-injection/debug/TLS/key-log/threadpool/native-loader environment variables to be absent, and the cwd package/version plus canary source bytes to match the running package. Executable regressions cover a trusted first PATH Node, an explicit absolute runtime Node, relative PATH resolution from the child cwd, a shadowing first Node, missing/empty targets, `NODE_OPTIONS`, debug/TLS/key-log/threadpool/native-loader overrides, and deterministic Windows PATH/PATHEXT behavior. Runtime-entry regressions require the actual packaged canary path and reject a same-bytes canary under another workspace path. Prerelease activation regressions separately require the canary's executing package root to canonicalize to the package root containing activation `runtime_entry`, so a workspace/developer invocation cannot generate prerelease evidence even when its entry bytes match. For all release channels the source contract also requires the existing daemon-owner verifier with candidate `expectedVersion`, exact runtime `expectedEntryScript`, exact `expectedNodeExecutable`, exact daemon-lock `expectedNodeVersion`, `verified_service_daemon`, and startup-readiness checks, so stable canaries cannot be evidenced from a source checkout while a different packaged daemon is active. The canary source contract further requires the same clean environment, imports from the activated runtime package, `process.cwd()` as the candidate/evidence data root, exact single-flag argv, and empty `process.execArgv`; the entrypoint regression spawns a harmless Node CLI option and requires rejection before live state access. `--state-dir`/`--workspace` overrides fail before state access because evidence does not encode those identities. Mutable checkout modules therefore cannot execute under the light exception and unrecorded local-state selection cannot become release evidence. The npm CLI resolver used inside the canary has separate tests for lifecycle-path rejection, running-Node layouts, and the Homebrew Cellar/package-manager-prefix split. Arbitrary shell commands have no generic zero-resource bypass.

```sh
npm run check:fast      # static, unit, contract, and architecture feedback
npm run check:platform  # fast plan plus cross-platform behavior and real-machine tests
npm run check           # complete suite; equivalent to check:full
```

The explicit task lists live in `scripts/check-plan.mjs`. The fast plan retains static analysis, policy, architecture, contracts, and focused unit behavior. The platform plan adds process, service, browser/application, state, managed-job, cryptographic, and real-machine behavior tests needed on macOS and Windows. The full-only plan adds coverage, browser-broker integration, package/install, stdio, Worker/OAuth, and real-browser navigation suites. In particular, a green fast plan is not evidence that the npm tarball has correct 0644/0755 modes or installability; `package:test` builds the actual manifest and rejects unexpected packaged file modes, and the install suite validates the consumer artifact. `npm run check` remains the authoritative complete gate.

Tests are verification inputs but are not npm tarball entries under the current `package.json.files` manifest. A test-only repository change therefore does not by itself change npm package bytes or require a synthetic package version; `release-impact:check` remains authoritative and still requires a version whenever `package.json`, `package-lock.json`, or any path selected by `package.json.files` changes. A source fix that requires a regression test is versioned because of its packaged source/documentation/metadata impact, not because `tests/` is implicitly shipped.

On macOS, `scripts/run-checks.mjs` re-executes the complete fast/platform/full verification process under `/usr/bin/caffeinate -i` before it captures verification inputs. The internal `MBM_CHECK_IDLE_SLEEP_GUARD` marker prevents recursive wrapping. This establishes an idle-system-sleep assertion for the whole verification lifetime so a short child timeout cannot expire only because the machine entered Idle Sleep between dispatch and settlement. That verification-lifetime guard is distinct from production ownership: authorized, schema-valid relay handlers hold a shared `/usr/bin/caffeinate -i -w <daemon-pid>` assertion for their full execution lifetime; the default thirty-minute rolling inactivity grace starts only after the last concurrent handler settles, and a new authorized handler cancels pending release so the full grace restarts after it settles. A remote process session extends the same daemon assertion from successful resource admission through child settlement. A remote account managed-job runner independently holds `/usr/bin/caffeinate -i -w <runner-pid>` only after its runner claim is confirmed and persisted ownership identifies an account-backed job, then retains it through terminal persistence; local managed jobs do not acquire that remote-continuity assertion, and the remote runner protection survives daemon reconnect/replacement. Runtime shutdown terminates process sessions before releasing the daemon assertion. The production thirty-minute relay grace is fixed rather than depending on shell-only environment inheritance that launchd does not persist as service configuration or treating relay heartbeats as user activity. None of these mechanisms claims to defeat explicit sleep or lid-close sleep; those still invalidate the usefulness of a live-machine verification run.

Successful child-task stdout/stderr is intentionally suppressed so a long green plan does not overwhelm an MCP response or hide the final status behind host truncation. Progress and timing remain visible. A failed task returns bounded head/tail diagnostics for both streams. Set `MBM_CHECK_VERBOSE=1` only when an operator explicitly needs live child output; verbose mode can be large and should be run through a process session when used remotely.

Remote execution carrier limits are separate from the verification plan itself. `run_process`/`run_local_command`/`exec_command` cap one detached process step at 600 seconds, while a complete `check:full` can legitimately exceed that wall-clock budget when a real install or integration dependency is slow. A remote release verification that may cross 600 seconds must therefore submit `npm run check:full` as a detached `start_job` step with a larger explicit step timeout and inspect it with `read_job`; an ordinary local terminal run is unaffected. The same rule applies below 600 seconds: a composite real-host/lifecycle/fault-injection verification with an uncertain or multi-phase upper bound must not be placed behind an arbitrary 300-second `exec_command` budget and then treat carrier SIGTERM as a test failure. Split independently terminal phases into durable job steps and size each step from the verifier's own bound plus settlement margin. Coherent short verification commands should be grouped into a repository umbrella command or one multi-step managed job rather than emitted as dozens of one-step remote carriers; this reduces host-visible event density without changing any verifier deadline or forcing a user-turn handoff. Hosted `read_job` pacing tests separately require the 40-second default, five-second terminal-detection poll, 30-second minimum nonterminal progress coalescing, hosted-only suppression of `current_step` wakeups, and preservation of local explicit-wait step progress. This does not widen any product foreground/process timeout—it prevents the verification carrier or host event stream from becoming the narrower continuity boundary than the suite being measured.

Generation-9 continuity coverage additionally requires short hosted durable-process acceptance to settle inside the original tool response when the job is already terminal, preserve the original `job_id`/recovery envelope if the optional settlement read is unavailable, and leave active jobs on the normal `read_job` path. Managed-job inventory tests must prove more than 50 newer terminal helpers cannot hide an older active job. Resource-admission tests must expose the current bounded waiter reason such as `cpu_pressure_window` without waiter identity/token/PID/path fields, and security-audit tests must aggregate recent tool density without argument/result content. macOS power-diagnostic coverage reduces representative `pmset` lines to bounded sleep intervals and requires a same-duration/same-resume-time runtime stall to classify as `matched_system_sleep` while a nonmatching pause remains unclassified. Idle-sleep-guard tests pin activity/grace/release timestamps and the coarse inactivity-expiry reason without extending the existing thirty-minute grace. These are diagnostic/recovery guarantees, not new timing verdicts for the user task.

The fast runner avoids a second npm process for package scripts that are exactly one simple `node ...` invocation and have no `pre<task>`/`post<task>` lifecycle hooks. It recreates the relevant npm lifecycle identity in the child environment; scripts containing shell syntax, lifecycle hooks, or non-Node commands still run through npm, so shell/package-manager semantics are not guessed. Parallel-safe fast tasks use a bounded worker pool that defaults to at most four workers and is further bounded by Node's `availableParallelism()`; `MBM_CHECK_CONCURRENCY` may explicitly select 1–16. Known process-heavy gates remain serial barriers. This preserves every fast-plan gate while removing repeated npm startup cost. In non-verbose plans ordinary successful child output remains suppressed, but `self-test` forwards only its sparse phase-start/phase-complete markers so a hosted hang identifies the active phase before an outer CI deadline.

Resource-admission regressions are first-class fast and critical-coverage gates. `resource-admission:test` covers Green/Yellow/Red pressure, absent optional pressure metrics, Linux `MemAvailable`/PSI parsing including default-reader/no-PSI behavior and sustained `psi_io_full_avg10 >= 60` as direct critical I/O-stall evidence, soft-versus-hard free-disk headroom, startup-window reservations, adaptive quick sampling, five-second I/O evidence reuse, bounded recovery when the atomically replaced cross-process host-sample cache changes generation during secure pathname verification, fail-closed exhaustion for persistent generation churn, valid and invalid persistent request contracts, stale ownership, priority aging, protected-queue diagnostics including the privacy-safe `drain_active` fairness signal, ordinary fit-aware head-of-line bypass, protected drain for an aged feasible waiter, impossible-old-request bypass, and fixed CPU fan-out above the best-case launch window. The latter proves an eight-worker fixed request on an idle eight-core interactive host fails immediately and non-retryably as `cpu_request_exceeds_launch_window`, a seven-worker request remains admissible, the impossible waiter cannot reserve starvation drain, and no retry sleep occurs. It also covers literal-shell-cwd versus dynamic-cwd contention scope, false heavy classification from ordinary filename arguments, and referenced wait timeout/in-flight abort/already-aborted behavior. It further proves nested lease-envelope accounting: parent coverage, child excess delta, parallel sibling summation, parent-loss recovery to full child cost, recent-CPU delta, same-key ancestor-only exemption, same-key sibling serialization, ancestry-sampling fallback, and a real coordinator acquisition where the requesting process is the live parent lease owner. Process-lifecycle coverage binds a real isolated group, releases the caller-side handle while that group is still alive, requires the durable reservation to remain, then proves ordinary pruning removes it after the group exits. Resource host, process ancestry, and resource-owner generation sampling is production-async-only: the old synchronous `sampleResourceHost`, Darwin sampler, process-parent sampler/cache, and `spawnSync` resource-probe transport are not retained as dormant APIs. Async host-probe tests require Darwin pressure probes to launch concurrently and keep a timer runnable while their child commands are pending; ancestry-cache tests require concurrent callers to share one in-flight system-wide process scan, refresh after the bounded TTL, and cache a failed/null sample only for that same TTL. Process-start snapshot tests require concurrent/current coordinator pruning to consume lock-external generation evidence, fail closed when a live PID is absent from the snapshot, and reclaim a proven PID reuse before numeric process-group liveness can override it. The expired beta.104 transaction-owner directory migration branch is no longer a current test surface. Script-classification regressions distinguish the actual executed entrypoint from later arguments: direct Node/Python coverage/verify roots and package-manager `check` scripts promote before fan-out, while interpreter module/eval modes and harmless scripts followed by heavy-looking filenames remain adaptive. Generic zero-resource admission is identity-bound: the standard absolute executables enumerated by `resource-light-command.mjs` qualify, and the exact current Node runtime receives the same light classification only for the argument-only `--version`/`-v` probe. All generic light invocations also require the hardened startup environment to exclude Node preload/profiler/cache overrides, TLS/key-log overrides, and POSIX/Darwin dynamic-loader injection variables; otherwise they remain adaptive. Arbitrary Node eval/scripts, lookalike Node paths, and the same `ps`/`uptime`/`sleep` basenames reached through PATH remain adaptive. `stat`, `df`, `which`, `printf`, `wc`, search/traversal commands, caller-controlled Git, `find`, `open`, and `osascript` remain adaptive because filesystem behavior, input size, options, helpers, state mutation, or child execution can make them unbounded. Arbitrary zsh/bash/sh/PowerShell/cmd invocations never receive the generic light bypass, including payloads that only appear to call a trusted inner executable. Background-priority tests require POSIX heavy background roots to use one `nice +5` wrapper and leave interactive roots unchanged. Canonical project-key tests require fixed v1 golden vectors plus a real path and a symlink alias to derive the same contention key. `resource-build-root:test` covers Cargo/SwiftPM/Xcode path/job controls, explicit override preservation, macOS no-index behavior, canonical cache identity, and the transaction rule that build-root preparation failure releases an already-acquired lease. `coverage:test` executes the direct resource fixtures and enforces dedicated thresholds across admission, hierarchy/coordinator accounting, process ancestry, canonical project identity, policy, waiters, profile/shell parsing, host pressure, wait liveness, staging, build-root/process admission, and request validation. Its V8 merge preserves explicitly covered ranges while letting a missing child range inherit the nearest enclosing execution count, and an exact-generation digest fails the run if source/test content, file mode, or symlink topology changes while coverage is being collected. Architecture release contracts prevent those fixtures, merge semantics, generation guard, or core threshold keys from disappearing. Runtime/managed-job suites separately prove leases bind real process trees and release through close, cancellation, timeout, and detached-job cleanup. `full-access:test` uses an isolated resource coordinator, a synthetic healthy-host sampler, and an explicit ten-second process-admission budget for its internal `LocalRuntime`; its separate detached-job observation window remains five minutes. Settlement polling imports the production managed-job terminal classifier rather than maintaining a second status list, so recovered/expired/cancelled-before-start terminal states cannot become five-minute false hangs. `local-self-test` keeps process-admission behavior deterministic instead of inheriting shared-host pressure: its runtime fixture uses an isolated coordinator, a synthetic healthy-host sampler, and a ten-second resource-admission budget on both one-shot and process-session boundaries. Its resource/managed-job CLI phase likewise avoids host pressure as a clock: execution-only jobs use the exact current-runtime `node --version` light probe, managed-job settlement shares one five-minute phase wall-clock budget, and only one terminal CLI `job read` is needed after direct persisted-state settlement. Daemon-fixture child exit waits are independently bounded at thirty seconds, and each self-test phase emits start/completion markers that the non-verbose verification runner forwards selectively so a hosted hang identifies its phase before an outer CI timeout. The five-minute resource-CLI phase bound and stdio detached-job observation window are test-harness ceilings, not production managed-job or user-task limits. Runtime/job command deadlines still start after admission, while ordinary production one-shot calls derive admission from 20% of their execution timeout with a two-second floor, ten-second ceiling, and never beyond the execution timeout. Owner-local process-session startup defaults to a ten-second cooperative wait; relay-origin `start_process` defaults to zero admission wait, performs one real admission decision, and returns retryable `unavailable` before spawn when pressure blocks it. Managed-job child steps default to ten minutes, may explicitly request up to six hours (`timeout_seconds=21600`), and start that execution timer only after resource admission. The runner's separate pre-spawn admission wait is capped by the shared thirty-minute durable-delivery contract; `read_job.current_phase=resource_admission` distinguishes that state from child execution, local/owner completed-step reads expose `resource_admission_ms` alongside total `duration_ms` while delegated non-owner reads omit that machine-user scheduling timing, and the release-contract suite binds the phase transition, owner-only timing projection, plus lease cleanup if post-admission status persistence fails. `runtime-handlers:test` asserts that ordinary `LocalRuntime` composition leaves both process-service overrides unset so those dynamic defaults are not accidentally replaced by a constructor constant. The resource-executing runtime in `agent-context-test` likewise uses an isolated coordinator, synthetic healthy-host sampling, and a ten-second test-only resource-admission budget; an architecture release contract prevents that deterministic isolation or short-bounded override from being silently removed.
Managed-job runner-log bounding is likewise isolated from host scheduling and suite-wide coverage instrumentation: the `bounded runner diagnostics` fixture uses a dedicated raw manager/root with `minimalEnv:true`, asserts its reviewed plan has `full_env=false` and no `NODE_V8_COVERAGE` step override, then launches the exact current-runtime `node --version` probe after pre-filling the runner log. This keeps the production rule intact that any Node instrumentation/preload environment makes a nominal version probe adaptive, while ensuring this test measures launch-time log trimming rather than shared CI pressure or coverage transport. The general managed-job test wrapper follows the same production boundary: it injects an empty `NODE_V8_COVERAGE` override only for `minimalEnv:false` fixtures that would otherwise inherit the parent coverage stream; `minimalEnv:true` fixtures receive no synthetic Node instrumentation key because their runner execution environment already strips it. The dependency-retention fail-closed setup likewise uses exact current-runtime `node --version`: it only needs a persisted successful upstream result before corrupting the dependent plan and therefore must not inherit unrelated host-pressure timing from an adaptive no-op. Same-daemon dependency-wait runner recovery is verified without a test-side `read_job` of the recovered upstream: persisted runner state must show one autonomous relaunch, then an independently waiting downstream must report a structured dependency failure identifying that recovered upstream as `failed/dependency_failed`.

Managed-job integration fixtures that genuinely need adaptive script semantics use a test-process-only runner launch seam instead of treating hosted machine pressure as part of those lifecycle assertions. `createManagedJobTestManager()` supplies a constructor-only `runnerSpawnProcess` function; it adds a Node `--import` hook to the runner process only, passing the hook as a canonical `file://` URL so Windows drive-letter paths cannot be misparsed as URL schemes. The hook redirects exactly the production runner's `./resource-admission.mjs` import to a fixture coordinator that subclasses the production implementation and changes only `sampleHost` to the shared synthetic healthy-host sampler. The hook is not inherited by managed-job children, is not expressible through MCP plans or environment settings, and is absent from `LocalRuntime` production construction. Dedicated resource-admission tests remain responsible for Green/Yellow/Red pressure and scheduling behavior.

The Wrangler command lifecycle fixture waits for the child `close` event before its test body settles, then removes its unique temporary root with Node's bounded recursive-removal retry support (`maxRetries: 5`, `retryDelay: 50`). This addresses transient Windows `EBUSY` and related filesystem lock windows after process/stdio settlement without inserting a fixed sleep or changing the production Wrangler command timeout and cleanup lifecycle.

The resource suite also injects hard-link/atomic-replace crash staging and requires exact-generation recovery. A still-live lease/waiter publisher must never be reclaimed; a transient publisher that completes during the fixed four-attempt staging-busy retry must let the reader continue, while a publisher that remains live after that budget still fails closed with the stable staging-busy classification. Process-admission coverage requires exhausted transaction/staging contention to project as retryable resource unavailability rather than an internal error, and `resourceAdmissionDiagnostic` must preserve the same meaning: a bounded diagnostic snapshot that loses a live transaction/staging lock race reports `snapshot_available=false`, retryable `unavailable`, and `reason=coordinator_busy` rather than generic `execution_failed`. Current transaction-lock coverage requires the writer to publish one owner-state regular file with the stable resource-coordinator purpose, token, and process identity. Current transaction-lock fixtures cover complete-before-visible owner-state files, waiting for a live prior owner, stale matching-owner reclamation, persistent multiple-hard-link rejection, and fail-closed handling of the obsolete directory shape. The legacy directory fixture additionally requires the directory and its owner bytes to remain unchanged after rejection, proving removal of automatic beta.104 quarantine/restore rather than merely hiding that path. Operation-budget regressions additionally require acquisition to stay within the caller's remaining admission budget while spawned-process lease bind/release may wait up to 30 seconds for ownership settlement. `managed-jobs:test` runs its destructive runner-kill scenarios inside a test-private coordinator/build root and deterministically holds that coordinator's transaction lock for 5.5 seconds during dead-runner recovery; the fixture itself gets 30 seconds to acquire the private lock before the measured hold begins, so scheduler delay cannot fail the setup before the old five-second product boundary is exercised. Recovery must then wait through that old internal deadline, run finally work exactly once after release, and remain successful both normally and under `NODE_V8_COVERAGE` instrumentation.

JavaScript syntax validation likewise avoids a child-process storm: one Node VM-module parser process parses the complete dynamically discovered `.js`/`.mjs` surface, then the Unix shell wrapper receives one `sh -n` check. The parser subprocess is started with Node's VM-module flag only for parsing and does not evaluate or link repository modules. This keeps syntax coverage equivalent to a parse-only gate while avoiding hundreds of `node --check` process launches.

Real process-tree fault injection should test the state transition, not consume minutes merely to reach it. Timeout fixtures therefore use short but scheduling-tolerant deadlines while still launching real descendants that ignore graceful termination and asserting forced cleanup, ownership checks, cancellation/recovery, and terminal persistence. Do not lengthen these fixture deadlines as a substitute for fixing readiness races; increase only the bounded readiness margin that has concrete cross-platform evidence. A lifecycle test that follows a public timeout must first wait within the production escalation budget for the previous tracker ownership to settle, then observe the new process as a tracker-count increase before terminating it; rejection observers are attached when the Promise is created so a fast signal cannot become an unhandled rejection. Security-critical session revocation/shutdown settlement waits keep their bounded deadline timer referenced, while ordinary output-observation waits remain unreferenced. Coverage fixtures must also avoid duplicate execution when a composite test already invokes the same subordinate suite.

The repository and product runtime require Node.js 26 and npm 12. `.node-version`, `.nvmrc`, `packageManager`, strict published `engines`, CLI startup validation, doctor, and CI keep execution on that baseline. `devEngines.runtime` warns rather than aborting metadata-only Node 24 automation so Dependabot can update the lockfile; this is not runtime support.

## Test design rules

- Tests should exercise the public boundary rather than only helper functions when practical.
- Lock, service lifecycle, state deletion, detached process, and credential changes require behavior-level concurrent or fault-injection coverage; source-string assertions are supplementary only.
- Every permission-expanding feature needs a denial test. Browser/application features also require a token/value/content non-disclosure assertion.
- Every bounded resource needs an over-limit test.
- Every multi-stage mutation needs a no-partial-commit test.
- Every remote call correlation or readiness change needs daemon replacement, incumbent-preservation, timeout, malformed-result, and cancellation coverage.
- Every durable workflow needs disconnect, cancellation, cleanup-failure, dead-runner, and plan-scrubbing coverage.
- Secret-bearing resource tests must assert absence of raw, path, base64, and hex forms from MCP-visible results.
- Logs and public metadata should be tested for absence of sensitive fields, arguments, outputs, and routine success noise—not only presence of expected fields.
- Cross-platform tests must avoid shell syntax, URL-path conversion, and executable-shim assumptions specific to one operating system. A fixture that injects a logical platform such as `darwin` or `win32` must not silently treat the physical CI host's UID, file-mode, executable-bit, signal-delivery, path, or service-manager semantics as evidence for that injected platform; inject the required host capability explicitly or gate only the assertion that the physical host cannot prove.
- Release-evidence privacy tests must inject private-looking but publication-safe paths/URLs/text and assert absence from every recovered-success projection and persisted record. Do not commit a real credential pattern merely to test redaction.
