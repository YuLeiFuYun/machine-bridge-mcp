# Testing strategy

The project treats transport, authorization, local authority, and state removal as separate failure domains.

## Independent privacy and deployment boundaries

The managed-job redaction gate covers macOS temporary-path aliases and case-varied Windows capture tails. The logging gate checks encoded sensitive query names, malformed encoding, harmless parameters, complete/truncated private-key bodies, and human/structured output. Deployment tests reject coerced account IDs and token-validity values, exercise exact file-count boundaries plus ignored-entry/depth overflow, and prove upload-success persistence before missing-URL or cleanup failure with restart and endpoint reconciliation. These are local regression oracles, not deployed release evidence.


## Interruption and authority boundaries

Worker security fixtures drain all 1,024 durable revocations over the bounded 64-message HTTPS channel and retain sequencing/acknowledgements. Infrastructure fixtures cover queue-pressure deferral, complete envelope-byte accounting, probing-versus-ready drain eligibility, metric overflow and monitor sequence rollover. Relay fixtures inject a stale socket-open event and require the replacement connection deadline to fire. OAuth/DPoP fixtures reject malformed types and URIs, contain asynchronous signature failures, and deny dispatch after token/client/account/family/expiry authority changes. These local faults supplement the complete Worker integration and candidate-bound live canary; they do not attribute every network reset or system suspension to an application defect.


## Required suites

The resource profile suite also pins the live-release exception discovered under multi-project contention and tightened after both npm `script-shell` and mutable-checkout review. Only exact direct Node argv `node <activated-runtime-package>/scripts/release-oauth-canary.mjs --allow-live-oauth-canary` may receive the `release-control` light profile. The script operand must be absolute and canonicalize to the running package's own canary; `node scripts/release-oauth-canary.mjs ...`, copied workspace canaries, npm/pnpm lifecycle invocation, shell wrappers, missing/extra argv, and lookalike entrypoints never receive release-control identity. Production admission also requires the resolved Node executable to canonicalize to the daemon's own `process.execPath`, startup-injection/debug/TLS/key-log/threadpool/native-loader environment variables to be absent, and the cwd package/version plus canary source bytes to match the running package. Executable regressions cover a trusted first PATH Node, an explicit absolute runtime Node, relative PATH resolution from the child cwd, a shadowing first Node, missing/empty targets, `NODE_OPTIONS`, debug/TLS/key-log/threadpool/native-loader overrides, and deterministic Windows PATH/PATHEXT behavior. Runtime-entry regressions require the actual packaged canary path and reject a same-bytes canary under another workspace path. Prerelease activation regressions separately require the canary's executing package root to canonicalize to the package root containing activation `runtime_entry`, so a workspace/developer invocation cannot generate prerelease evidence even when its entry bytes match. For all release channels the source contract also requires the existing daemon-owner verifier with candidate `expectedVersion`, exact runtime `expectedEntryScript`, exact `expectedNodeExecutable`, exact daemon-lock `expectedNodeVersion`, `verified_service_daemon`, and startup-readiness checks, so stable canaries cannot be evidenced from a source checkout while a different packaged daemon is active. The canary source contract further requires the same clean environment, imports from the activated runtime package, `process.cwd()` as the candidate/evidence data root, exact single-flag argv, and empty `process.execArgv`; the entrypoint regression spawns a harmless Node CLI option and requires rejection before live state access. `--state-dir`/`--workspace` overrides fail before state access because evidence does not encode those identities. Mutable checkout modules therefore cannot execute under the light exception and unrecorded local-state selection cannot become release evidence. The npm CLI resolver used inside the canary has separate tests for lifecycle-path rejection, running-Node layouts, and the Homebrew Cellar/package-manager-prefix split. Arbitrary shell commands have no generic zero-resource bypass.

```sh
npm run check:fast      # static, unit, contract, and architecture feedback
npm run check:platform  # fast plan plus cross-platform behavior and real-machine tests
npm run check           # complete suite; equivalent to check:full
```

The explicit task lists live in `scripts/check-plan.mjs`. The fast plan retains static analysis, policy, architecture, contracts, and focused unit behavior. The platform plan adds process, service, browser/application, state, managed-job, cryptographic, and real-machine behavior tests needed on macOS and Windows. The full-only plan adds coverage, browser-broker integration, package/install, stdio, Worker/OAuth, and real-browser navigation suites. In particular, a green fast plan is not evidence that the npm tarball has correct 0644/0755 modes or installability; `package:test` builds the actual manifest and rejects unexpected packaged file modes, and the install suite validates the consumer artifact. `npm run check` remains the authoritative complete gate.

During `check:full`, the verification runner owns one private, generation-bound V8 coverage directory for the full invocation and passes it only to tasks that directly execute the curated standalone coverage fixtures; unrelated verification tasks never receive that coverage environment. The `coverage:test` gate reuses reports produced by those coverage-relevant tasks that already completed in that same invocation, then executes only coverage fixtures whose evidence is still missing before applying the unchanged module thresholds. The reuse context is parent-process-bound, permission-checked, tied to the exact coverage-input generation, and removed when the full plan settles. A standalone `npm run coverage:test` has no such context, creates its own private directory, executes its complete fixture list, and therefore remains independently authoritative.

Windows publication hard-timeout coverage deliberately keeps deterministic barrier semantics separate from provider proof. The unit-level process-tree fixture requires `terminateProcessTreeAndWait()` to remain unsettled until the forced `taskkill.exe /PID ... /T /F` helper reaches terminal `close(0)` and to fail closed on helper failure or settlement timeout; it must not add a second post-success process-enumeration command whose own latency changes the meaning of that five-second barrier. `publish-npm:test` is the unchanged end-to-end resistant-descendant proof: after publication reports a confirmed hard timeout, the descendant that ignores graceful termination must be unable to execute its delayed marker. The Linux/macOS/Windows platform matrix is authoritative for that operating-system behavior; a local non-Windows pass cannot replace the hosted Windows result.

Tests are verification inputs but are not npm tarball entries under the current `package.json.files` manifest. A test-only repository change therefore does not by itself change npm package bytes or require a synthetic package version; `release-impact:check` remains authoritative and still requires a version whenever `package.json`, `package-lock.json`, or any path selected by `package.json.files` changes. A source fix that requires a regression test is versioned because of its packaged source/documentation/metadata impact, not because `tests/` is implicitly shipped.

On macOS, `scripts/run-checks.mjs` re-executes the complete fast/platform/full verification process under `/usr/bin/caffeinate -i` before it captures verification inputs. The internal `MBM_CHECK_IDLE_SLEEP_GUARD` marker prevents recursive wrapping. This establishes an idle-system-sleep assertion for the whole verification lifetime so a short child timeout cannot expire only because the machine entered Idle Sleep between dispatch and settlement. That verification-lifetime guard is distinct from production ownership: authorized, schema-valid relay handlers hold a shared `/usr/bin/caffeinate -i -s -w <daemon-pid>` assertion for their full execution lifetime; `-s` requests the stronger system-sleep assertion only effective on AC, while `-i` remains the baseline Idle Sleep assertion. The default thirty-minute rolling inactivity grace starts only after the last concurrent handler settles, and a new authorized handler cancels pending release so the full grace restarts after it settles. A remote process session extends the same daemon assertion from successful resource admission through child settlement. A remote account managed-job runner independently holds `/usr/bin/caffeinate -i -s -w <runner-pid>` only after its runner claim is confirmed and persisted ownership identifies an account-backed job, then retains it through terminal persistence; local managed jobs do not acquire that remote-continuity assertion, and the remote runner protection survives daemon reconnect/replacement. Runtime shutdown terminates process sessions before releasing the daemon assertion. The production thirty-minute relay grace is fixed rather than depending on shell-only environment inheritance that launchd does not persist as service configuration or treating relay heartbeats as user activity. None of these mechanisms claims to defeat explicit sleep, lid-close sleep, or battery-mode system sleep; those still invalidate the usefulness of a live-machine verification run.

Successful child-task stdout/stderr is intentionally suppressed so a long green plan does not overwhelm an MCP response or hide the final status behind host truncation. Progress and timing remain visible. A failed task returns bounded head/tail diagnostics for both streams. Set `MBM_CHECK_VERBOSE=1` only when an operator explicitly needs live child output; verbose mode can be large and should be run through a process session when used remotely.

Remote execution carrier limits are separate from the verification plan itself. `run_process`/`run_local_command`/`exec_command` cap one detached process step at 600 seconds, while a complete `check:full` can legitimately exceed that wall-clock budget when a real install or integration dependency is slow. A remote release verification that may cross 600 seconds must therefore submit `npm run check:full` as a detached `start_job` step with a larger explicit step timeout and inspect it with `read_job`; an ordinary local terminal run is unaffected. The same rule applies below 600 seconds: a composite real-host/lifecycle/fault-injection verification with an uncertain or multi-phase upper bound must not be placed behind an arbitrary 300-second `exec_command` budget and then treat carrier SIGTERM as a test failure. Split independently terminal phases into durable job steps and size each step from the verifier's own bound plus settlement margin. Coherent short verification commands should be grouped into a repository umbrella command or one multi-step managed job rather than emitted as dozens of one-step remote carriers; this reduces host-visible event density without changing any verifier deadline or forcing a user-turn handoff. Hosted `read_job` pacing tests separately require the 40-second default, five-second terminal-detection poll, 30-second minimum nonterminal progress coalescing, hosted-only suppression of `current_step` wakeups, and preservation of local explicit-wait step progress. This does not widen any product foreground/process timeout—it prevents the verification carrier or host event stream from becoming the narrower continuity boundary than the suite being measured.

Continuity coverage requires short hosted durable-process acceptance to settle inside the original tool response when the job is already terminal, preserve the original `job_id`/recovery envelope if the optional settlement read is unavailable, and leave active jobs on the normal `read_job` path. The same shared initial-settlement helper is now exercised through the actual hosted `start_job` runtime handler: a short terminal multi-step job must return `follow_up_read_required=false`, while active or unavailable optional settlement preserves its durable identity and normal `read_job` continuation. Relay coverage separately drives more than eight real reconnects and requires `recent_outages` to remain newest-first and capped at eight, while a first-stage Pong timeout cleared by application confirmation without WSS replacement must leave that completed-outage history unchanged. Fallback handover coverage must retain per-outage `https_fallback_taken_over` and `https_fallback_takeover_ms` for multiple takeover episodes, project false/zero for a no-takeover episode between them, and prove that Worker synthesized recovery binds the top-level last-takeover outage number only when it exactly matches the recovering outage. Multi-attempt coverage requires `disconnected_at` to stay fixed at the first outage transition, `last_disconnect_at` to advance through later failed reconnects, and `duration_ms` to remain first-disconnect-to-ready; a synthetic protocol-Ping dispatch failure also proves that the bounded `*_at_start` liveness fields freeze the first-disconnect phase. Local producer and Worker sanitizer fixtures bound every episode field, strip unknown/private keys, and require Worker ready promotion to synthesize the just-completed current outage that could not yet have been present in the pre-ready hello with the same first/final timestamp and start-liveness semantics. Managed-job inventory tests must prove more than 50 newer terminal helpers cannot hide an older active job. Resource-admission tests must expose the current bounded waiter reason such as `cpu_pressure_window` without waiter identity/token/PID/path fields, and security-audit tests must aggregate recent tool density without argument/result content. macOS power-diagnostic coverage reduces representative `pmset` lines to bounded sleep intervals and requires a same-duration/same-resume-time runtime stall to classify as `matched_system_sleep` while a nonmatching pause remains unclassified. Idle-sleep-guard tests pin activity/grace/release timestamps and the coarse inactivity-expiry reason without extending the existing thirty-minute grace. These are diagnostic/recovery guarantees, not new timing verdicts for the user task.

The fast runner avoids a second npm process for package scripts that are exactly one simple `node ...` invocation and have no `pre<task>`/`post<task>` lifecycle hooks. It recreates the relevant npm lifecycle identity in the child environment; scripts containing shell syntax, lifecycle hooks, or non-Node commands still run through npm, so shell/package-manager semantics are not guessed. Parallel-safe fast tasks use a bounded worker pool that defaults to at most four workers and is further bounded by Node's `availableParallelism()`; `MBM_CHECK_CONCURRENCY` may explicitly select 1–16. Known process-heavy gates remain serial barriers. This preserves every fast-plan gate while removing repeated npm startup cost. In non-verbose plans ordinary successful child output remains suppressed, but `self-test` forwards only its sparse phase-start/phase-complete markers so a hosted hang identifies the active phase before an outer CI deadline.

Verification children deliberately do not inherit owner runtime configuration that can change the behavior under test before a fixture opts in: `MBM_RELAY_PROXY`, `MBM_RELAY_FALLBACK_PROXY`, `MBM_DEBUG`, `MBM_MACOS_BACKGROUND_VISUAL_BACKEND`, and `MBM_MACOS_TRUST_BROKER` are removed case-insensitively from both the ordinary check runner and nested critical-coverage children. Dedicated relay, debug, experimental-native-input, and trust-broker fixtures inject their required configuration explicitly; the opt-in live macOS smoke commands remain separate from the generic check plans. Standard `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` state, execution-surface provenance, and explicit verification controls such as `MBM_CHECK_CONCURRENCY` are not globally stripped because package/network tests, durable-carrier provenance, and verifier resource control legitimately depend on them.

Resource-admission regressions are first-class fast and critical-coverage gates. `resource-admission:test` covers Green/Yellow/Red pressure, absent optional pressure metrics, Linux `MemAvailable`/PSI parsing including default-reader/no-PSI behavior and sustained `psi_io_full_avg10 >= 60` as direct critical I/O-stall evidence, soft-versus-hard free-disk headroom, startup-window reservations, adaptive quick sampling, five-second I/O evidence reuse, one shared resource-state JSON reader used by both the atomically replaced host-sample cache and ResourceCoordinator state, bounded four-observation recovery only when secure pathname verification reports `MBM_IDENTITY_CHANGED`, immediate fail-closed behavior for permission/symlink/multiple-hard-link/malformed-content failures, fail-closed exhaustion for persistent generation churn, valid and invalid persistent request contracts, stale ownership, priority aging, protected-queue diagnostics including the privacy-safe `drain_active` fairness signal, ordinary fit-aware head-of-line bypass, protected drain for an aged feasible waiter, impossible-old-request bypass, and fixed CPU fan-out above the best-case launch window. The latter proves an eight-worker fixed request on an idle eight-core interactive host fails immediately and non-retryably as `cpu_request_exceeds_launch_window`, a seven-worker request remains admissible, the impossible waiter cannot reserve starvation drain, and no retry sleep occurs. It also covers literal-shell-cwd versus dynamic-cwd contention scope, false heavy classification from ordinary filename arguments, and referenced wait timeout/in-flight abort/already-aborted behavior. It further proves nested lease-envelope accounting: parent coverage, child excess delta, parallel sibling summation, parent-loss recovery to full child cost, recent-CPU delta, same-key ancestor-only exemption, same-key sibling serialization, ancestry-sampling fallback, and a real coordinator acquisition where the requesting process is the live parent lease owner. Process-lifecycle coverage binds a real isolated group, releases the caller-side handle while that group is still alive, requires the durable reservation to remain, then proves ordinary pruning removes it after the group exits. Resource host, process ancestry, and resource-owner generation sampling is production-async-only: the old synchronous `sampleResourceHost`, Darwin sampler, process-parent sampler/cache, and `spawnSync` resource-probe transport are not retained as dormant APIs. Async host-probe tests require Darwin pressure probes to launch concurrently and keep a timer runnable while their child commands are pending; ancestry-cache tests require concurrent callers to share one in-flight system-wide process scan, refresh after the bounded TTL, and cache a failed/null sample only for that same TTL. Process-start snapshot tests require concurrent/current coordinator pruning to consume lock-external generation evidence, fail closed when a live foreign PID is absent from the snapshot, and reclaim a proven foreign PID reuse before numeric process-group liveness can override it. The coordinator's own `process.pid` is a separate identity boundary: waiter/provisional-lease pruning and atomic staging-publisher recovery must use `currentProcessStartTimeMs()` for that PID and must not let a mismatched external snapshot self-prune the running coordinator into `fairness_wait` or delete a live waiter/lease staging file; mismatched foreign-PID evidence remains reclaimable, missing foreign evidence remains fail-closed, and a same-PID staging artifact whose timestamp predates the current process generation is still reclaimed. The parallel waiter cancellation/wakeup fixture also injects the known current-process generation so its short observer window measures resource-change signalling rather than a real all-process scan. The obsolete transaction-owner directory migration branch is absent. Script-classification regressions distinguish the actual executed entrypoint from later arguments: direct Node/Python coverage/verify roots and package-manager `check` scripts promote before fan-out, while interpreter module/eval modes and harmless scripts followed by heavy-looking filenames remain adaptive. Generic zero-resource admission is identity-bound: the standard absolute executables enumerated by `resource-light-command.mjs` qualify, and the exact current Node runtime receives the same light classification only for the argument-only `--version`/`-v` probe. All generic light invocations also require the hardened startup environment to exclude Node preload/profiler/cache overrides, TLS/key-log overrides, and POSIX/Darwin dynamic-loader injection variables; otherwise they remain adaptive. Arbitrary Node eval/scripts, lookalike Node paths, and the same `ps`/`uptime`/`sleep` basenames reached through PATH remain adaptive. `stat`, `df`, `which`, `printf`, `wc`, search/traversal commands, caller-controlled Git, `find`, `open`, and `osascript` remain adaptive because filesystem behavior, input size, options, helpers, state mutation, or child execution can make them unbounded. Arbitrary zsh/bash/sh/PowerShell/cmd invocations never receive the generic light bypass, including payloads that only appear to call a trusted inner executable. Background-priority tests require POSIX heavy background roots to use one `nice +5` wrapper and leave interactive roots unchanged. Canonical project-key tests require fixed v1 golden vectors plus a real path and a symlink alias to derive the same contention key. `resource-build-root:test` covers Cargo/SwiftPM/Xcode path/job controls, explicit override preservation, macOS no-index behavior, canonical cache identity, and the transaction rule that build-root preparation failure releases an already-acquired lease. `coverage:test` executes the direct resource fixtures and enforces dedicated thresholds across admission, hierarchy/coordinator accounting, process ancestry, canonical project identity, policy, waiters, profile/shell parsing, host pressure, wait liveness, staging, build-root/process admission, and request validation. Its V8 merge preserves explicitly covered ranges while letting a missing child range inherit the nearest enclosing execution count, and an exact-generation digest fails the run if source/test content, file mode, or symlink topology changes while coverage is being collected. Architecture release contracts prevent those fixtures, merge semantics, generation guard, or core threshold keys from disappearing. Runtime/managed-job suites separately prove leases bind real process trees and release through close, cancellation, timeout, and detached-job cleanup. `full-access:test` uses an isolated resource coordinator, a synthetic healthy-host sampler, and an explicit ten-second process-admission budget for its internal `LocalRuntime`; its separate detached-job observation window remains five minutes. Settlement polling imports the production managed-job terminal classifier rather than maintaining a second status list, so recovered/expired/cancelled-before-start terminal states cannot become five-minute false hangs. `local-self-test` keeps process-admission behavior deterministic instead of inheriting shared-host pressure: its runtime fixture uses an isolated coordinator, a synthetic healthy-host sampler, and a ten-second resource-admission budget on both one-shot and process-session boundaries. Its resource/managed-job CLI phase likewise avoids host pressure as a clock: execution-only jobs use the exact current-runtime `node --version` light probe, managed-job settlement shares one five-minute phase wall-clock budget, and only one terminal CLI `job read` is needed after direct persisted-state settlement. Daemon-fixture child exit waits are independently bounded at thirty seconds, and each self-test phase emits start/completion markers that the non-verbose verification runner forwards selectively so a hosted hang identifies its phase before an outer CI timeout. The five-minute resource-CLI phase bound and stdio detached-job observation window are test-harness ceilings, not production managed-job or user-task limits. Runtime/job command deadlines still start after admission, while ordinary production one-shot calls derive admission from 20% of their execution timeout with a two-second floor, ten-second ceiling, and never beyond the execution timeout. Owner-local process-session startup defaults to a ten-second cooperative wait; relay-origin `start_process` defaults to zero admission wait, performs one real admission decision, and returns retryable `unavailable` before spawn when pressure blocks it. Managed-job child steps default to ten minutes, may explicitly request up to six hours (`timeout_seconds=21600`), and start that execution timer only after resource admission. The runner's separate pre-spawn admission wait is capped by the shared thirty-minute durable-delivery contract; `read_job.current_phase=resource_admission` distinguishes that state from child execution, local/owner completed-step reads expose `resource_admission_ms` alongside total `duration_ms` while delegated non-owner reads omit that machine-user scheduling timing, and the release-contract suite binds the phase transition, owner-only timing projection, plus lease cleanup if post-admission status persistence fails. `runtime-handlers:test` asserts that ordinary `LocalRuntime` composition leaves both process-service overrides unset so those dynamic defaults are not accidentally replaced by a constructor constant. The resource-executing runtime in `agent-context-test` likewise uses an isolated coordinator, synthetic healthy-host sampling, and a ten-second test-only resource-admission budget; an architecture release contract prevents that deterministic isolation or short-bounded override from being silently removed.

The process-parent probe contract is tested through injected platform command results, including the conservative `null` fallback when the bounded OS probe fails. The unit/coverage gate does not require the developer or CI host's real process table to complete inside the production probe deadline; host-pressure behavior is exercised by the dedicated resource-admission and runtime diagnostic boundaries instead. The elastic admission retry/re-expansion fixture similarly injects its known current-process start generation so its one-second synthetic retry budget measures admission state transitions rather than a real system-wide process-generation scan, including under `NODE_V8_COVERAGE`. Likewise, remote process-read exit and cooldown state are pinned deterministically with synthetic session state and explicit waiter notifications, including output wakeup, `wait_for_exit` ignoring ordinary output, cooldown preservation, and terminal clearing. The few remaining real child-process fixtures use a test-only spawn seam that clears inherited `NODE_V8_COVERAGE` from their `node -e` children while leaving the parent test and production modules instrumented; this keeps nested coverage overhead out of child scheduling semantics without changing execution-surface propagation. Those fixtures retain only the hosted one-second wait clamp with a scheduling-tolerant lower bound rather than using sub-second child timers or scheduler-dependent upper bounds as correctness evidence.

The full-only stdio integration keeps its ordinary protocol/request response timeout at five seconds so discovery, schema, validation, and read-only regressions still fail promptly. Requests that deliberately cross the real process-admission boundary use a separate 20-second `PROCESS_TOOL_RESPONSE_WAIT_MS` harness budget. This is an observer ceiling, not a product timeout change: a five-second `run_process`/`exec_command` execution may first consume the documented local resource-admission window, while `start_process` may wait up to the local process-session admission window before spawn. The integration therefore must not use the product execution timeout itself as the total request/transport/settlement observation deadline.
Managed-job runner-log bounding is likewise isolated from host scheduling and suite-wide coverage instrumentation: the `bounded runner diagnostics` fixture uses a dedicated raw manager/root with `minimalEnv:true`, asserts its reviewed plan has `full_env=false` and no `NODE_V8_COVERAGE` step override, then launches the exact current-runtime `node --version` probe after pre-filling the runner log. This keeps the production rule intact that any Node instrumentation/preload environment makes a nominal version probe adaptive, while ensuring this test measures launch-time log trimming rather than shared CI pressure or coverage transport. The general managed-job test wrapper follows the same production boundary: it injects an empty `NODE_V8_COVERAGE` override only for `minimalEnv:false` fixtures that would otherwise inherit the parent coverage stream; `minimalEnv:true` fixtures receive no synthetic Node instrumentation key because their runner execution environment already strips it. The dependency-retention fail-closed setup likewise uses exact current-runtime `node --version`: it only needs a persisted successful upstream result before corrupting the dependent plan and therefore must not inherit unrelated host-pressure timing from an adaptive no-op. Same-daemon dependency-wait runner recovery is verified without a test-side `read_job` of the recovered upstream: persisted runner state must show one autonomous relaunch within a forty-second fixture window that covers all three 10.1-second production reconciliation attempts plus scheduler margin, then an independently waiting downstream must report a structured dependency failure identifying that recovered upstream as `failed/dependency_failed`.

Managed-job integration fixtures that genuinely need adaptive script semantics use a test-process-only runner launch seam instead of treating hosted machine pressure as part of those lifecycle assertions. `createManagedJobTestManager()` supplies a constructor-only `runnerSpawnProcess` function; it adds a Node `--import` hook to the runner process only, passing the hook as a canonical `file://` URL so Windows drive-letter paths cannot be misparsed as URL schemes. The hook redirects exactly the production runner's `./resource-admission.mjs` import to a fixture coordinator that subclasses the production implementation and changes only `sampleHost` to the shared synthetic healthy-host sampler. The hook is not inherited by managed-job children, is not expressible through MCP plans or environment settings, and is absent from `LocalRuntime` production construction. The resource-replacement recovery fixture adds one narrower test-only boundary on top of that seam: its dedicated runner receives `NODE_V8_COVERAGE=""` while the parent managed-job suite and ordinary runner fixtures remain instrumented, so the fixture's ten-second readiness observer measures resource materialization/recovery rather than nested coverage latency in the production process-start generation sampler. The real process-tree timeout fixture uses the same narrow isolation principle with its own manager/job root: only that detached runner clears inherited `NODE_V8_COVERAGE`, so the fixture measures the production SIGTERM → ownership-proof → SIGKILL lifecycle without turning nested V8 instrumentation delay into process-group liveness evidence; the parent suite and all other managed-job runners remain covered. Dedicated resource-admission tests remain responsible for Green/Yellow/Red pressure and scheduling behavior.

The Wrangler command lifecycle fixture waits for the child `close` event before its test body settles, then removes its unique temporary root with Node's bounded recursive-removal retry support (`maxRetries: 5`, `retryDelay: 50`). This addresses transient Windows `EBUSY` and related filesystem lock windows after process/stdio settlement without inserting a fixed sleep or changing the production Wrangler command timeout and cleanup lifecycle.

The resource suite also injects hard-link/atomic-replace crash staging and requires exact-generation recovery. A still-live lease/waiter publisher must never be reclaimed; a transient publisher that completes during the fixed four-attempt staging-busy retry must let the reader continue, while a publisher that remains live after that budget still fails closed with the stable staging-busy classification. Process/startup-lock coverage separately reproduces the exclusive-publisher post-link crash residue: a live two-link owner is readable only through the descriptor-verified reserved-alias token without deleting that alias, a proven stale canonical owner may be reclaimed while the old alias remains, and an arbitrary hard link outside the reserved namespace still fails closed. Process-admission coverage requires exhausted transaction/staging contention to project as retryable resource unavailability rather than an internal error, and `resourceAdmissionDiagnostic` must preserve the same meaning: a bounded diagnostic snapshot that loses a live transaction/staging lock race reports `snapshot_available=false`, retryable `unavailable`, and `reason=coordinator_busy` rather than generic `execution_failed`. Current transaction-lock coverage requires the writer to publish one owner-state regular file with the stable resource-coordinator purpose, token, and process identity. Current transaction-lock fixtures cover complete-before-visible owner-state files, waiting for a live prior owner, stale matching-owner reclamation, persistent multiple-hard-link rejection, and fail-closed handling of the obsolete directory shape. The legacy directory fixture additionally requires the directory and its owner bytes to remain unchanged after rejection, proving removal of automatic legacy-directory quarantine/restore rather than merely hiding that path. Operation-budget regressions additionally require acquisition to stay within the caller's remaining admission budget while spawned-process lease bind/release may wait up to 30 seconds for ownership settlement. `managed-jobs:test` runs its destructive runner-kill scenarios inside a test-private coordinator/build root and deterministically holds that coordinator's transaction lock for 5.5 seconds during dead-runner recovery; the fixture itself gets 30 seconds to acquire the private lock before the measured hold begins, so scheduler delay cannot fail the setup before the old five-second product boundary is exercised. Recovery must then wait through that old internal deadline, run finally work exactly once after release, and remain successful both normally and under `NODE_V8_COVERAGE` instrumentation.

JavaScript syntax validation likewise avoids a child-process storm: one Node VM-module parser process parses the complete dynamically discovered `.js`/`.mjs` surface, then the Unix shell wrapper receives one `sh -n` check. The parser subprocess is started with Node's VM-module flag only for parsing and does not evaluate or link repository modules. This keeps syntax coverage equivalent to a parse-only gate while avoiding hundreds of `node --check` process launches.

Real process-tree fault injection should test the state transition, not consume minutes merely to reach it. Timeout fixtures therefore use short but scheduling-tolerant deadlines while still launching real descendants that ignore graceful termination and asserting forced cleanup, ownership checks, cancellation/recovery, and terminal persistence. Do not lengthen these fixture deadlines as a substitute for fixing readiness races; increase only the bounded readiness margin that has concrete cross-platform evidence. A lifecycle test that follows a public timeout must first wait within the production escalation budget for the previous tracker ownership to settle, then observe the new process as a tracker-count increase before terminating it; rejection observers are attached when the Promise is created so a fast signal cannot become an unhandled rejection. Security-critical session revocation/shutdown settlement waits keep their bounded deadline timer referenced, while ordinary output-observation waits remain unreferenced. Coverage fixtures must also avoid duplicate execution when a composite test already invokes the same subordinate suite.

The repository and product runtime require Node.js 26 and npm 12. `.node-version`, `.nvmrc`, `packageManager`, strict published `engines`, CLI startup validation, doctor, and CI keep execution on that baseline. `devEngines.runtime` warns rather than aborting metadata-only Node 24 automation so Dependabot can update the lockfile; this is not runtime support.

### Hosted timing and recovery

Ordinary daemon tools default to 20 seconds plus the separate Worker settlement margin. Configurable browser/application calls default to 20 seconds; compound `computer_observe`/`computer_act` default to 30 seconds, with a 45-second explicit maximum. Their fixtures require one end-to-end deadline rather than a fresh budget at each phase. Pending-call tests reject non-finite, non-positive, non-integer, and over-contract operation/reconnect delays before timer/alarm mutation.

Relay tests distinguish the five-second protocol-level transport probe, outbound dispatch progress, confirmed Pong delivery and independent application confirmation. A generic late error must not erase a specific timeout cause. Result expiry permanently withdraws proof of safe missing-ID redelivery; absence of evidence cannot authorize a second side effect.

Hosted `read_process` keeps its one-second blocking limit and fifteen-second would-block pacing; `wait_for_exit` ignores ordinary stdout wakeups. Live reads report `status_polling_mode=paced_followup`. Active hosted `read_job` uses `status_polling_mode=bounded_followup` and `host_turn_handoff_recommended=false`; terminal reads report `terminal`. The default wait is 40 seconds and the maximum 60, with reconciliation headroom and original-deadline accounting. Progress can shorten a long-poll, while unchanged nonterminal state is coalesced. Cached-schema compatibility must fail before side effects or preserve the accepted job and exact recovery action.

Discovery/subscription fixtures require current schema/version metadata, zero cache TTL, bounded account/room capacity and idempotent release. Opening a stream supplies only server-side evidence: server-opened subscription evidence cannot prove external client receipt. When workspace governance freezes actions, the **Action control** snapshot after the supported refresh/review path supplies publication evidence; opaque host-internal cache inspection is intentionally excluded from release acceptance. A harmless invocation probe must also cross a previous argument or behavior boundary, as specified in [Releasing](RELEASING.md).

### Durable recovery and monitor authority

Retention fixtures require that a store saturated with 512 such promised terminals returns typed retryable `limit_exceeded` without eviction. Follow-up-required terminals retain their 24-hour recovery promise; active jobs and dependency-pinned state remain protected. Account-version quota tests prove a seventeenth genuinely new carrier is rejected before state publication or process launch, while valid same-key replay succeeds at quota. A statusless deterministic directory is an incomplete publication rather than replay; it must pass quota again. Cross-process last-slot races admit exactly one carrier.

Dependency tests use persisted upstream state, a deterministic transient-failure clock and the fixed 45-second recovery grace. Integrity/witness/missing-state failures remain fail closed. Runner tests require autonomous same-job recovery, result-first terminal reconstruction and no duplicate finally work. Full-access diagnostics delay terminal publication to prove their private job directory remains until the identity-aware runner inventory settles, and inject shutdown failure to prove temporary environment state is restored.

MCP Apps tests require issued → activated → claimed monitor ownership, principal/job binding, bounded durable monitor state and status-only projection. Neither results, command/output/path data nor recovery/control capabilities may reach the View. Storage or cleanup failure must preserve an already accepted core result and authority revocation. Only an active, explicitly persisted `task_supervisor` with a current claim can recommend task handoff; ordinary monitors do not own execution or the rest of an assistant task. Widget tests cover one-time render binding, watchdogs, teardown, stale/replaced claims and bounded retry without job resubmission.

## Test design rules

- Tests should exercise the public boundary rather than only helper functions when practical.
- Lock, service lifecycle, state deletion, detached process, and credential changes require behavior-level concurrent or fault-injection coverage; source-string assertions are supplementary only.
- Every permission-expanding feature needs a denial test. Browser/application features also require a token/value/content non-disclosure assertion.
- Every bounded resource needs an over-limit test.
- Every multi-stage mutation needs a no-partial-commit test.
- Every remote call correlation or readiness change needs daemon replacement, incumbent-preservation, timeout, malformed-result, and cancellation coverage.
- Every durable workflow needs disconnect, cancellation, cleanup-failure, dead-runner, recovery-attribution, and plan-scrubbing coverage.
- Secret-bearing resource tests must assert absence of raw, path, Base64, Base64URL, and hexadecimal forms from MCP-visible results.
- Logs and public metadata should be tested for absence of sensitive fields, arguments, outputs, and routine success noise—not only presence of expected fields.
- Cross-platform tests must avoid shell syntax, URL-path conversion, and executable-shim assumptions specific to one operating system. A fixture that injects a logical platform such as `darwin` or `win32` must not silently treat the physical CI host's UID, file-mode, executable-bit, signal-delivery, path, or service-manager semantics as evidence for that injected platform; inject the required host capability explicitly or gate only the assertion that the physical host cannot prove.
- Release-evidence privacy tests must inject private-looking but publication-safe paths/URLs/text and assert absence from every recovered-success projection and persisted record. Do not commit a real credential pattern merely to test redaction.

## Package manifest

`npm run package:test` executes a real silent `npm pack --dry-run --json`, requires clean parseable JSON, rejects sensitive local artifacts, credential-like file classes, and generated Worker type declarations, validates every packaged mode as `0644` or `0755`, and verifies that required runtime, script, browser-extension, privacy, governance, and release files are present. Hardened bootstrap downloads distinguish a 60-second no-progress failure from a slow transfer that continues making progress, while retaining an independent absolute attempt ceiling; install smoke is therefore allowed to exceed one minute on a degraded registry path without treating sustained progress as a retryable stall. A fake Wrangler JavaScript entrypoint terminates at a controlled deployment boundary, so the probe exercises startup without mutating a live account. Package testing is full-plan-only; installation smoke runs in the Ubuntu full plan, the macOS/Windows platform plan, and package audit.

The complete plan deliberately starts with the real `sbom:test` before the ordinary fast/platform tasks. Besides validating CycloneDX shape, this makes npm's own dependency-tree validation a cheap generation preflight: a checkout whose ignored `node_modules` still reflects an older manifest/lock fails before managed-job, coverage, install, browser, or Worker integration work. Canonical GitHub/npm publication additionally runs hardened lockfile-only `npm ci`; the early SBOM gate remains useful for normal developer/CI runs and for detecting any later dependency-tree drift.

Architecture tests require `shell:test`, `lint:test`, `lint`, and `install:test` to remain in the complete check pipeline and reject non-exact direct dependency ranges.

The stdio integration test also sends an oversized line, verifies bounded rejection, and confirms that the next valid request is still processed.
