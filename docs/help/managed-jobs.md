stage_job persists a validated non-running draft only. It is not an approval workflow and cannot be promoted from the terminal; execution uses start_job when the effective account policy permits it, or an explicit local machine-mcp job submit PLAN.json operation.

Hosted start_job requires a caller-chosen idempotency_key before dispatch. Accepted hosted managed jobs return principal-bound recovery_key and control_key capabilities; read_job requires recovery_key, cancel_job requires control_key, and a job_id alone is not remote managed-job authority. If its acceptance response is ambiguous, retry exactly the same start_job arguments with the same key rather than creating a second logical submission or switching to another execution path. Recovery errors name the credential source as the original request and do not echo the key value. After durable acceptance, the original hosted start_job response waits through the short advertised managed-job initial-settlement window; a job that becomes terminal inside that window returns its terminal result with follow_up_read_required=false, while an active job preserves the same job_id/recovery envelope with follow_up_read_required=true for normal read_job continuation. This coalescing changes host-visible response count only: durable ownership, dependencies, resource admission, six-hour step ceilings, and recovery semantics are unchanged. Local/stdio start_job keeps the underlying optional-key API without the hosted settlement wait. When an MCP Apps-capable active start_job reports ui_monitor_candidate=true plus ui_monitor_render_tool=render_job_monitor and a fresh ui_monitor_id, treat that monitor as an optional job-status surface rather than automatic task handoff. If remaining same-response work needs this job's terminal result, do not render the monitor; preserve job_id plus recovery_key and continue bounded server-paced read_job follow-up. Render only when the current assistant task can deliberately transfer this job's status polling without needing its terminal result for remaining same-response work. When intentionally rendering, call render_job_monitor once with the accepted job_id, recovery_key, and exact pre-issued ui_monitor_id. The render tool verifies existing read authority, activates the already-issued correlation ID, and mounts the Job Monitor; do not depend on any render result projection being visible to the planner. Immediately pass the same start_job ui_monitor_id on the next read_job. A matching active read for an ordinary job may report ui_monitor_claimed=true, status_polling_mode=ui_monitor, host_turn_handoff_recommended=false, and follow_up_read_required=false after the current View completed its handshake with hostCapabilities.serverTools and claimed the same monitor instance using the original recovery capability. Those fields transfer duplicate status polling for this job only; they do not require ending unrelated or still-actionable assistant work. An explicitly persisted continuation_mode=task_supervisor is the sole exception: declare it only when the durable job's own reviewed plan already encapsulates every remaining noninteractive task action. Machine Bridge can validate the persisted declaration, active state, and current View claim but cannot infer conversation-level task completeness; that completeness remains an owner/caller semantic assertion. After a current View claim is proven, an active task-supervisor read may report host_turn_handoff_recommended=true because the durable supervisor already owns the remaining execution lifecycle. The monitor still has status-only authority and gains no execution or capability authority. The mounted View continues status reads through the app-only read_job_monitor tool rather than the model-visible read_job surface; each app read uses the fixed 40-second server-paced wait and returns only a bounded lifecycle-status projection, never step output, command text, paths, nested job results, or recovery/control capabilities. The render-input recovery_key remains the View's read authority but is not forwarded to the daemon or rendered as status, and the View clears that in-memory capability on teardown. A transient client-to-Worker read failure is retried by the View with bounded backoff without resubmitting the managed job. Optional monitor-coordination storage failure after start_job/read_job has already produced a durable result must not reclassify that result: issuance falls back to ordinary non-UI continuation and unprovable claim state keeps model-side read_job continuation active. A stale claim with another monitor ID and hosts without a proven current claim retain the normal bounded same-response follow-up contract.

For durable cross-job ordering, prefer start_job.depends_on over shell loops that wait for files or markers. Hosted dependency references require an exact dependency_recovery mapping carrying the upstream job's recovery_key; the Worker verifies and strips that capability before daemon dispatch. A dependent runner remains queued in current_phase=dependency_wait without spawning its main child until all referenced managed jobs succeed; dependency_pending_count is progress observed by hosted read_job and is coalesced by the same nonterminal progress pacing as other active-state changes. If an upstream job later fails, the dependent settles with result.error_class=dependency_failed rather than blind-waiting for an artifact that can never appear. During dependency_wait, a secure state read classified as permission_denied, identity_changed, or generic resource_unavailable receives a fixed 45-second recovery grace; one successful read clears that grace, while persistent unavailability fails closed as dependency_unavailable and missing/integrity/witness-invalid evidence remains immediate failure. Staged or already-failed dependencies are rejected before acceptance. Active dependency plans pin the referenced retained job records against capacity pruning. This is a continuity mechanism, not a reason to shorten the overall user task or force a new user turn.

Hosted read-only status and diagnostic tools must not be used as busy loops. For a known managed job, use read_job with its recovery_key and the server-side paced long-poll by default: a relay-origin active read waits inside Machine Bridge for up to the advertised managed-job read interval. Terminal settlement returns on the next bounded progress poll, but nonterminal changes are coalesced for at least the advertised thirty-second progress interval (or the caller's explicitly shorter wait), and current_step-only churn does not wake the host call by itself. This keeps multi-step long jobs observable without turning every short local step into a host-visible event. Use wait_ms=0 only for an intentional immediate checkpoint. Public hosted read_job.wait_ms is capped at 60000 ms; longer jobs keep the same job_id and issue another server-paced read rather than one overlong host request. Interactive process sessions use the separately paced read_process contract: the one-second actual output/exit blocking cap remains, while a repeated would-block request inside the fifteen-second cooldown stays inside that same MCP call until output/exit or the cooldown boundary rather than returning a rapid running checkpoint. Bounded same-response follow-up is allowed when the current task needs terminal state or additional output. Hosted list_jobs is aggregate-only and intentionally cannot rediscover lost job handles. Do not switch among list_jobs, server_info, diagnose_runtime, or other status surfaces merely to evade pacing. Per-call wait survival and aggregate host-response lifetime are separate constraints: do not infer that a long task can remain in one assistant response merely because each individual read succeeds. Do not infer or preempt a host/tool deadline from elapsed wall-clock time. While tool calls continue to be accepted and the task still needs the result, bounded same-response follow-up may continue; if an actual host/tool boundary ends the response, preserve the durable job/session recovery credentials and resume that same operation later instead of resubmitting its side effect. A planned local-daemon restart may settle an in-flight hosted read_job as retryable unavailable with recovery.mode=read_same_job and the original job_id; after reconnect, hosted callers must read that same job_id with its preserved recovery_key instead of resubmitting the job's business side effect. A typed read_job not_found means the retained job record is unavailable, not that the underlying operation definitely never ran; do not blindly replay it.

For ordinary one-step remote process work whose child execution fits the 600-second process limit, exec_command, run_process, and run_local_command first commit a durable managed job, then keep the original hosted tool call open for the short advertised initial-settlement window. Acceptance transfers execution to durable ownership without forcing the current assistant response to end. If the helper settles inside that window, its terminal status/result is returned in the same tool response and no separate read_job event is required; if it remains active, the response keeps the same job_id/recovery envelope and normal read_job continuation applies. This reduces the common helper-plus-read double event without weakening durable ownership or changing the child timeout. For one coherent non-interactive workflow that needs several local commands, prefer one repository-native umbrella command or one multi-step start_job (or the smallest practical number of start_job plans) instead of emitting a chain of one-step process calls. Host-visible tool-event density is a continuity resource: batching reduces host traffic without shortening the underlying task or step lifetime. When the current task needs the result, bounded same-response read_job follow-up is allowed only when follow_up_read_required remains true; do not busy-loop or use repeated list_jobs as a substitute polling surface, and do not infer a host/tool deadline from elapsed wall-clock time. Cooperative machine-user admission is a separate pre-spawn interval and may wait up to 30 minutes; read_job.current_phase=resource_admission means no child for that step has started yet. Hosted one-step process carriers cap aggregate captured stdout/stderr at 32768 bytes; when complete large output is required, redirect it to a file and consume it with read_file, whose hosted complete serialized result is capped at 65536 bytes with whole-line next_start_line pagination. These one-step process carriers use lower-priority terminal retention than explicit managed jobs so helper-command churn reclaims completed helper history before displacing explicit durable recovery results when such helper history is available; the managed-job store remains bounded to 512 retained states. A hosted helper whose current response still requires read_job continuation is non-evictable under capacity pruning for the fixed 24-hour undelivered-result grace because Machine Bridge explicitly told the caller to follow that durable handle. If all 512 retained states are non-evictable, new admission returns the existing typed retryable limit_exceeded backpressure instead of deleting promised recovery evidence. Once Machine Bridge produces a terminal hosted response for that helper, whether during initial settlement or a later read_job, the private marker is downgraded to the shorter thirty-minute bounded newest-16 transient delivery reserve because only outer response-delivery uncertainty remains; a still-pending terminal also becomes removable after the 24-hour grace expires. Local/stdio list_jobs keeps its detailed primary jobs window capped at 50 and its recent_process_recovery handles capped at 16, prioritizing durable recovery state ahead of transient helper history. Hosted list_jobs removes those job IDs/names/handles and returns aggregate retained/capacity/activity state only; preserve the recovery_key delivered with acceptance and use read_job on that known capability-bound job after a real host/tool boundary. Owner/local capacity diagnostics distinguish durable_terminal from transient_terminal without exposing job identities. Use start_job for policy-authorized multi-step plans, job-scoped temporary_files, explicit resource injection, idempotent finally_steps, or a step that legitimately needs an execution budget above 600 seconds. Detached jobs continue after MCP disconnects and daemon replacement; for hosted later recovery preserve job_id plus recovery_key together with status/current_phase, and hand those credentials back only after an actual host/tool boundary is observed, external input or authorization is required, or the user explicitly requested a checkpoint.

Managed-job resource redaction is defense in depth, not a guarantee against transformed or partial secret output. Use capture_output=discard for steps that may echo credentials.

Do not impose a one-checkpoint turn boundary and do not infer a host/tool deadline from elapsed wall-clock time; continue bounded hosted follow-up while calls are accepted and the task still needs the result. WebSocket remains the preferred daemon transport. Verified ready traffic resumes immediately, but reconnect attempt history resets only after 5 seconds of generation-stable readiness; a shorter ready/close flap retains its prior exponential backoff position. A protocol-level Ping is attempted every 5 seconds, its full 10-second Pong deadline begins only after the local WebSocket sender confirms that Ping was written, and a separate 30-second dispatch bound detects a locally stuck send queue. One missed dispatched Pong enters a 15-second application-heartbeat confirmation stage before WSS is rebuilt. Only protocol Pong or application Pong is bidirectional transport proof; unrelated inbound application traffic updates receive-side liveness but cannot clear transport suspicion. Diagnosed local event-loop stalls use their separate recovery grace. If no verified WSS is ready, the same root-certified ephemeral device identity can establish the signed HTTPS daemon fallback. Fallback requests bind the fixed route/origin/server/version, one-time 30-second nonce and timestamp, and exact body SHA-256. Ordinary standby/ready fallback requests use a 7-second request deadline; exact-generation takeover requests use a 3-second deadline until verified readiness so one stale-network timeout, the first failure backoff, and the two takeover exchanges needed for readiness remain inside the existing 15-second new-call recovery window. Healthy verified WSS schedules no recurring HTTPS fallback polls. Active fallback uses a 12-second liveness window, 5-second ordinary ready-idle cadence, 30-second successful-standby cadence, bounded 1/2/4/5-second failure backoff, and hard 750 ms minimum request-start interval. HTTP 429/503 Retry-After is bounded to one hour; a monotonic not-before deadline prevents queued work, takeover, interrupts, and stop/start from accelerating retries. Candidate, probing, and verified-ready are distinct. A signed same-instance takeover may retire a Worker-side zombie WSS only after candidate preconditions pass. The daemon reconciles resume_calls, processes ready_ack, returns sequenced https_ready, and only then returns resume_calls_ack; the Worker does not dispatch ordinary work through HTTPS before verified readiness. Bidirectional contiguous transport sequences make an HTTP response retry retransmit the same envelope and discard duplicates before business handling. A resume_calls_ack.missing_ids entry is emitted only while the daemon still has a fail-closed proof that the ID has neither active-call nor retained-result ownership after replacement readiness. If a completed-but-unacknowledged result expires or recovery ownership otherwise becomes unsafe, that call ID enters bounded private replay-safety evidence and is no longer advertised as daemon-proven missing; unrelated resumed IDs remain eligible for transparent recovery while their own non-execution proof is intact. Diagnostics expose only aggregate replay-safety state: automatic_redelivery_safe becomes false whenever any unsafe-call tombstone exists or global redelivery is disabled, unsafe_call_tombstones reports only the bounded aggregate count, and global_redelivery_disabled identifies only the fail-closed exhaustion state; no call IDs or result content are exposed. While a safe missing entry exists, the initiating request remains live, and at least one second of the original execution budget remains, the Worker may retransmit exactly that same call ID, arguments, authority, and a reduced timeout. If safe redelivery cannot be accepted it falls back to retryable unavailable with side_effects_started=false. Calls that may have executed, retained results, different-daemon calls, and ambiguous mutations are never automatically replayed. A new daemon-backed call may wait at most 15 seconds for verified recovery, and that measured recovery interval is deducted from the original execution budget rather than extending the hosted foreground envelope. The separate application heartbeat remains 25 seconds with a 75-second application-silence timeout, and Worker WebSocket daemon liveness is a wider 90-second fallback. Ordinary daemon-backed tools default to 20 seconds of remote execution plus a separate five-second Worker settlement margin; compound computer_observe and computer_act default to 30 seconds, and configurable browser/application foreground tools may explicitly request at most 45 seconds. Remote run_process, run_local_command, and exec_command remain durable-first one-step jobs with a 10-second acceptance budget, a separate pre-spawn resource-admission wait of up to 30 minutes, and an independently bounded 1–600-second detached execution timeout. read_job.current_phase=resource_admission means that managed runner is still waiting before child spawn.
