# Computer Use

Machine Bridge Computer Use is a snapshot-bound control layer above the existing browser and desktop automation backends. It does not replace the browser broker, extension, macOS Accessibility implementation, or their low-level tools.

The design goal is to make GUI actions stateful and verifiable:

```text
observe -> bind target to snapshot -> preflight -> dispatch -> verify -> observe post-state
```

A successful input dispatch is not treated as proof that the requested user-visible or business effect occurred.

## Tools

### `computer_observe`

Creates one bounded observation and returns an opaque `snapshot_id`. Snapshot publication is the final observation settlement point: after the asynchronous browser/application capture finishes, cancellation is checked again before the snapshot enters the bounded store or consumes an id. A cancelled observe therefore cannot leave an actionable snapshot behind for a later `computer_act` call.

Browser observations contain:

- the existing executable DOM/actionability refs used by the trusted-input backend;
- a real Chromium Accessibility tree when the paired extension supports `computer_observation_v1`;
- DOMSnapshot-derived layout boxes, clickability, and paint order joined through `backendDOMNodeId`;
- conservative `action_ref` links from Accessibility nodes to executable DOM refs only when role/name/geometry matching is unambiguous;
- private snapshot bindings from those same **high-confidence** fused refs to Chromium `backendDOMNodeId` values. Correlation score and executable evidence are separate: `high` requires strong box overlap (IoU at least 0.7), no conflict between non-empty role/name evidence, and at least one exact role or name agreement. Center-point proximity or moderate overlap may still contribute to a useful `medium` observational correlation, but cannot authorize input; likewise, perfect geometry with a conflicting accessible name remains non-executable. A medium-confidence AX↔DOM correlation may remain visible as observational `action_ref` evidence, but it never receives an executable backend-node binding. The daemon independently requires `action_ref_confidence=high` before accepting any private backend id, so a stale or regressed extension cannot promote a medium heuristic match into trusted input. The raw backend ids are stripped from the public Computer Use observation; for `click`, `double_click`, `hover`, ref-to-ref `drag`, and ref-anchored `scroll`, the internal path can resolve `DOM.getContentQuads` to viewport coordinates and send trusted DevTools input even when a semantic endpoint is inside an accessible child frame;
- global cross-frame salience selection for executable DOM controls: each accessible frame contributes a bounded probe, then the aggregate `max_elements` budget is assigned to the highest-value controls across the whole page instead of being divided by frame traversal order;
- the selected tab identity, URL, document epoch, viewport, and frame tree;
- an optional native MCP screenshot, enabled by default and normally captured through `Page.captureScreenshot` in the same serialized DevTools session;
- explicit capture metadata describing navigation coherence and any legacy fallback;
- capability flags describing which grounding modes are actually implemented.

The Accessibility tree is used for richer semantic understanding; action dispatch still flows through constrained snapshot refs/trusted-input paths. For a fused semantic ref, Computer Use may privately use its snapshot-bound backend-node binding to obtain content quads; the public observation strips `backend_dom_node_id`, and callers cannot supply a backend id or raw CDP method. The low-level public `browser_action` contract is unchanged.

Application observations contain:

- one bounded macOS Accessibility inspection;
- snapshot-scoped refs (`a0`, `a1`, ...);
- process/frontmost state;
- optional window-local Accessibility geometry;
- a best-effort target-window PNG by default when Screen Recording/window capture is available;
- explicit native visual-point backend status (`visual_point_configured`, `visual_point_probed`, `snapshot_bound_visual_points`, and a bounded `visual_point_error_class`). A screenshot by itself never implies that native pixel dispatch is available.

Surface-specific arguments are strict. Browser-only arguments are rejected for application observations and application-only arguments are rejected for browser observations.

Snapshots are process-local, bounded to 64 recent entries, and expire after ten minutes measured by the daemon process monotonic clock. Wall-clock adjustment cannot extend or prematurely expire snapshot authority. They are intentionally not durable job state.

### `computer_act`

Requires the exact `snapshot_id` produced by `computer_observe` plus the same `surface`.

Page/application actions normally target a semantic snapshot ref. Browser `click`, `double_click`, `hover`, and `scroll` can additionally target a `normalized_viewport` point from the exact screenshot carried by the referenced snapshot, but only when that screenshot came from the navigation-coherent CDP capture path. Browser `drag` adds a required `destination` from the **same** snapshot. Its source and destination must use the same evidence class: ref-to-ref or point-to-point. Mixed ref/point drag is rejected instead of silently combining different grounding guarantees. Browser `scroll` takes bounded CSS-pixel `delta_x`/`delta_y` wheel deltas and requires at least one non-zero component; the target is the wheel anchor, so a ref can select a nested/virtualized scroll container while a point can target canvas or custom-drawn content. Raw CSS, arbitrary JavaScript, raw CDP methods, free-form AX selectors, device-pixel coordinates, and coordinates not bound to a Computer Use snapshot are not accepted.

The unified action schema is interpreted strictly by action, not merely by surface. Browser `value`/`value_resource` is accepted only for `fill`, `type_text`, and `select`; `key` is accepted only for `press`; `url` is accepted only for `navigate`; `destination` is accepted only for browser `drag`; `delta_x`/`delta_y` are accepted only for browser `scroll`; targetless navigation rejects target/input-only parameters instead of silently ignoring them. Application values are accepted only for `set_value` and `keystroke`, while `activate` rejects a target. The internal backend-node delegate repeats the sensitive-field checks so an accidental pointer action cannot resolve and forward a secret value even if an upper layer regresses.

Before dispatch:

- browser actions verify that the original tab still exists and has the same URL. Targetless `navigate`, `reload`, `back`, and `forward` also carry that observed URL privately through the daemon and re-check it in the extension immediately before the navigation mutation API, so a concurrent user navigation after daemon preflight wins instead of being overwritten;
- the top-frame per-document epoch must match whenever it is available, so a same-URL reload/replacement is rejected before input dispatch. `reload`, `back`, and `forward` additionally require both a successful epoch read and the private observed Navigation API history-entry key. The key binds the snapshot to the exact current history-list slot, closing same-document/same-URL traversal races that URL+document epoch cannot distinguish. Both authorities are carried privately through `BrowserOperationService`; for snapshot-bound history actions the fixed renderer module revalidates URL + document epoch + current Navigation API entry key, requires `navigation.canGoBack`/`canGoForward` for directional traversal, and synchronously invokes `navigation.reload()`, `navigation.back()`, or `navigation.forward()` in that same JS turn. This removes the prior service-worker await gap between history evidence collection and mutation dispatch. Missing/changed evidence, an unavailable requested history direction, or an unavailable Navigation API fails closed before dispatch, while loss of the renderer mutation response after invocation is classified as an unknown outcome and is never replayed through `chrome.tabs.*`. Ordinary non-Computer-Use browser history actions retain the generic `chrome.tabs` path. Neither the key nor other private authority fields are projected in the public Computer Use observation. Explicit `navigate(URL)` remains bound to the observed tab identity/URL but does not require the old document/history entry, because the requested destination is itself explicit;
- browser refs must still be attached;
- visual point actions require the same viewport dimensions/scale, an unoffset/unpinched visual viewport, and the same document epoch as the screenshot snapshot;
- browser drag preflights both endpoints. Point drag revalidates the exact screenshot once inside the trusted-input debugger session before any `Input.*` command. Ref drag independently revalidates both frame-document/ref identities and proves both backend-node content quads are already inside the current viewport before dispatch;
- browser scroll preflights its anchor with the same evidence strength. Point scroll revalidates the exact screenshot immediately before the wheel event. Ref scroll revalidates frame-document/ref identity and requires the backend-node content quad to already be inside the current viewport. It does **not** call `DOM.scrollIntoViewIfNeeded`: silently repositioning the anchor would be a separate mutation before the requested wheel effect;
- application refs are resolved back to their observed Accessibility identity and re-checked against the live UI;
- duplicate Accessibility identities preserve the observed occurrence index.

A Computer Use snapshot is one-shot mutation authority. Synchronous argument validation and read-only preflight happen before consumption, but immediately after preflight and before entering any browser/application mutation backend, `computer_act` atomically claims and removes that exact snapshot-store generation. Two concurrent acts can therefore inspect the same snapshot during read-only preflight, but only one can acquire dispatch authority; the other fails before mutation. Once the lower mutation handoff is attempted, the original snapshot is never restored, even if the backend reports a definite last-hop pre-dispatch failure or the later post-observation is cancelled. Continue only from the returned `post_snapshot_id`, or observe again. The existing `snapshot_missing_or_expired` conflict reason is retained for compatibility and also covers already-consumed snapshot authority.

After dispatch, Computer Use attempts a post-observation. To keep long trajectories bounded, browser post-observations capture 180 executable DOM elements and 180 Chromium Accessibility nodes by default, then return `post_observation_detail=summary` plus a bounded semantic delta. Application post-observations also default to a compact summary, retaining up to 24 salience-ranked snapshot refs plus the bounded semantic delta. The complete post observation is still retained behind `post_snapshot_id`; callers that genuinely need the complete tree can request `post_observation_detail=full`.

Post-action images use a separate `post_screenshot` policy. The default `auto` omits the image for an ordinary semantically verifiable action, but includes it for a snapshot-bound visual-point action, explicit `expect.visual_change`, or an ambiguous/unknown dispatch outcome where visual evidence can help recovery. `always` and `never` provide explicit control. The legacy `include_post_screenshot` boolean remains as a mutually exclusive compatibility override (`true` = `always`, `false` = `never`). This keeps image history from growing on every action while preserving screenshots exactly where they carry additional evidence. `post_screenshot_included` reports whether native image content is actually present in the returned result, not merely whether the selected policy requested an image.

Computer Use also applies the ordinary Machine Bridge tool-result byte ceiling **before publishing new snapshot authority**. If an otherwise valid observation would exceed that ceiling only because of its screenshot, the image is omitted, screenshot-bound point authority is revoked, and the still-bounded semantic snapshot is published. If a post-action image would overflow the result, the image is likewise omitted from both the returned post observation and the stored continuation snapshot while dispatch/effect settlement and `post_snapshot_id` are preserved. A still-oversized action result is compacted to bounded settlement/continuation/retry fields rather than discarding a completed mutation outcome or encouraging replay. `result_budget_compacted=true` and `post_screenshot_omitted_reason=tool_result_budget` identify this downgrade.

`observed_diff.semantic_delta` reports bounded added, removed, and changed controls. Browser delta identity is scoped by **top document epoch + extension frame id + that frame's own document epoch/URL + ref**. A same-URL child-frame reload therefore removes the old frame-document ref and adds the replacement ref even if both page worlds happen to assign the same string such as `e1`. Within an unchanged frame document, stable refs report mutable changes such as enabled/checked/focus/geometry and semantic-identity changes such as role/name/id separately. `observed_diff.frame_epoch_changed` reports whether the bounded extension-frame epoch map changed between snapshots (or `null` when frame coverage is insufficient). If the top document epoch changes, old refs are likewise treated as removed and new refs as added rather than pretending identity survived navigation. Application deltas use private selector-occurrence identity and also compare private owner-window bounds; an owner-window migration is surfaced only as `changed_fields:["owner_window"]`, never as global coordinates. Application `semantic_changed` is derived from this identity-aware delta rather than from public JSON alone, so a sibling-window migration cannot disappear merely because the visible role/name/state stayed the same. Sample lists are bounded even when counts are larger.

Every successful post-capture also returns a `continuation` record. Browser refs are **frame-document scoped**, not globally unique strings. `previous_target_ref_reusable=true` now requires the same top document epoch, the same target extension frame id with the same frame document epoch+URL, the same ref in that frame, and continued semantic identity. A sibling frame containing the same `e1`, a replacement child document that generates a new `e1`, or a same-object SPA repurpose such as `Save`→`Delete` cannot inherit the old target. `stable_ref_namespace` is true only when the top epoch and the complete bounded frame-epoch map both remain stable; target-specific `target_frame_epoch_same` and `target_identity_continues` explain the narrower reuse decision. The record also includes bounded added/changed/removed refs, delta truncation, and whether a fresh observe is recommended. If post-state capture fails, continuation is explicitly unavailable and re-observation is recommended. Application refs remain snapshot-scoped, so continuation never claims that old `aN` strings are reusable. Instead, when the acted target has a private semantic identity, continuation attempts a conservative mapping into the **new** post snapshot. `mapped_post_target_ref` is emitted only when application/process identity, private selector, original occurrence, and owner-window evidence continue; if either snapshot has owner-window evidence, both sides must have matching bounds. The same owner-window rule is used by post-condition lookup and private value readback, so a same-selector control in a sibling window cannot confirm the original target's focus/checked/value effect. Screen position is deliberately not part of cross-snapshot continuity so legitimate layout movement within the same owner window does not break identity. A salience reorder can therefore map old `a1` to new `a0`, while the old `a1` remains invalid. Target removal, sibling-window migration, or missing identity evidence yields no mapping and callers must replan from the post observation.

Browser `expect.target_state` uses the live wait only as a bounded convergence wait; the wait result alone is never final proof. The post snapshot must still show the target in the same frame document with the same semantic identity, and the requested visible/enabled/editable/checked state is read again from that post element. If the target is absent from an incomplete/truncated post projection, verification is `inconclusive` and the effect stays `unknown`. A changed frame epoch or semantic identity cannot confirm a positive target state. Explicit `detached`/`hidden` remains compatible with the old target actually disappearing. This prevents a recycled same-ref control from satisfying the original action's effect contract merely because it happens to expose the requested state.

Action results also return `retry_guidance`. It is deliberately conservative: `same_action_retry_allowed` is always false. A confirmed effect produces `disposition=do_not_retry`; a completed dispatch with no explicit effect contract also produces `do_not_retry` rather than treating missing verification as a reason to replay. An ambiguous dispatch or an unobserved expected effect uses `disposition=use_post_snapshot` only when a usable post snapshot exists; otherwise it returns `reobserve_before_retry`. When application continuation has a conservative target mapping, retry guidance repeats the **new** `mapped_post_target_ref` with `mapped_ref_for_replanning_only=true`; this is a pointer for inspecting/replanning from `post_snapshot_id`, never permission to replay the prior action. The `next_step` is either `continue_from_post_snapshot` or `computer_observe`, so callers do not have to infer recovery policy from free-form prose.

## Dispatch status and effect status

`computer_act` reports two independent states.

`dispatch_status`:

- `completed`: the backend reported that its dispatch sequence completed;
- `unknown`: the backend may have started dispatching before an error or timeout made the final input outcome ambiguous.

`effect_status`:

- `confirmed`: the requested or intrinsic post-condition was observed;
- `not_observed`: dispatch completed, but the requested effect was not observed within the verification window;
- `unknown`: there was no verifiable post-condition, dispatch itself was ambiguous without confirming evidence, or post-state could not be observed.

An `unknown` result must not be automatically replayed. Re-observe before deciding whether another action is safe.

Post-observation verifier checks expose their deterministic evidence channel as `verification.post_checks[].evidence_source`. Stable values are `browser_tab_state`, `browser_semantic`, `application_process`, `application_workspace`, `application_accessibility`, and `screenshot`. The field identifies where the check was grounded; it does not increase confidence by itself, and screenshot evidence is not allowed to substitute for available semantic/process state. This keeps state-based verification distinguishable from visual fallback evidence when an agent decides how much trust to place in an observed effect.

Examples of intrinsic verification in v1:

- browser `check` expects the target to become checked;
- browser `uncheck` expects the target to become unchecked;
- application `activate` expects the process to become frontmost;
- application `focus` expects the target to become focused.

Callers can also provide explicit expectations.

Browser expectations:

- `url_contains`;
- `url_changed`;
- page `text`;
- `load_state`;
- `target_state` such as visible, enabled, checked, or detached;
- explicit `semantic_change`, which compares the semantic observation fingerprint;
- explicit `visual_change`, which compares SHA-256 fingerprints of the baseline and post-action screenshots.

Browser verification is deliberately two-stage. `url_contains`, page `text`, `load_state`, and `target_state` can be checked by the bounded browser wait backend; `url_changed`, `semantic_change`, and `visual_change` require the actual post observation/diff. A successful wait never substitutes for a pending post-observation condition. Until every requested post condition has actually been computed, verification remains `post_check_pending` and cannot produce `effect_status=confirmed`. If post capture fails after the wait succeeded, the effect is `unknown` and recovery requires a fresh observation rather than treating the missing diff/screenshot as success.

`visual_change` is intentionally opt-in. It requires screenshots in both the referenced and post-action observations and is useful for canvas/WebGL effects that do not produce a reliable DOM state change. Animation, video, cursors, clocks, or other incidental rendering can also change a screenshot, so visual change alone should only be requested when rendering change is the intended effect. The screenshot digest is computed locally from the actual returned image bytes and is included in capture metadata; no screenshot is synthesized when image capture failed.

Application expectations:

- `frontmost`;
- `target_exists`;
- `target_enabled`;
- `target_focused`;
- `target_checked`;
- `target_selected`;
- `target_expanded`;
- `target_value_matches` for exact private readback of a non-sensitive `set_value` target;
- explicit `semantic_change` and `visual_change`.

Application verification uses `verify_timeout_seconds` as a bounded read-only settlement window measured by a monotonic deadline; wall-clock adjustment cannot enlarge or collapse the verification budget. After the mutation has been dispatched exactly once, Computer Use may repeat only the post-action application observation while the requested condition is still unsettled or a post capture transiently fails. The verifier performs at most nine post-action captures with exponential 100/200/400/800 ms backoff (800 ms cap). The first mandatory post observation keeps the normal read-only action timeout so a cold Accessibility inspection is not killed merely because the default verification window is shorter; only subsequent retry captures are reduced to the remaining verification budget. A newer successful verification snapshot replaces and discards the prior internal retry snapshot, so only the final continuation snapshot remains addressable. The mutation is never replayed by this loop. Cancellation or a later verification/capture failure after dispatch stops further read-only verification and makes an incomplete result `unknown`; it never overwrites the already-known dispatch settlement or turns the issued mutation into a retryable cancellation. If an earlier unmatched snapshot exists but later captures become unavailable before the bounded verifier settles, that older snapshot is retained as continuation evidence but is not strong enough to claim `not_observed`. For `target_value_matches`, the retained exact-value handle remains one-shot: a missing post-target binding can be re-observed before comparison, but once exact AX value comparison is attempted the handle is not consumed again. Exact AX value readback is also capped to the remaining verification budget; the cold-start timeout exception applies only to the first mandatory post observation, so a short `verify_timeout_seconds` cannot be followed by an unrelated full-length value-readback timeout.

## Snapshot identity

Browser refs are stable backend refs, but Computer Use still binds them to a particular Computer Use snapshot. The wrapper recovers the correct `frame_id` from that snapshot rather than asking the model to carry frame coordinates independently.

Application refs are intentionally snapshot-scoped. The macOS Accessibility backend does not currently expose durable element handles, so Computer Use derives a selector from the observed Accessibility identity and uses an occurrence index only when duplicate identities exist.

Application process identity is also snapshot-scoped and is stronger than a PID. The private snapshot binds both the observed PID and an opaque process-generation token derived from the public macOS `proc_pidinfo(PROC_PIDTBSDINFO)` process-birth timestamp (`pbi_start_tvsec/pbi_start_tvusec`). The fixed JXA helper and fixed native input helper compute the same token from that ABI; there is no `launchDate`/`/bin/ps` coarse fallback. If the exact birth identity cannot be read, process-bound authorization fails closed. The token is never exposed in the public observation. Accessibility inspection, mutation, exact value readback, window recapture, and native visual input all require the generation to remain equal. The native pointer helper additionally retains the validated `NSRunningApplication` instance and compares it with the current same-PID instance before every gesture boundary, so a PID recycled between snapshot validation and a later down/up/drag/scroll event cannot inherit the old snapshot's authority.

Snapshot IDs are opaque and have no authorization meaning. Existing policy and operation-authorization checks still apply to every Computer Use call.

## Security and authority

The Computer Use layer does not introduce arbitrary code execution.

It deliberately does not expose:

- caller-supplied browser JavaScript;
- caller-selected CDP methods;
- caller-supplied AppleScript/JXA;
- raw/unbound pixel clicks; snapshot-bound visual points use normalized viewport coordinates and only the fixed trusted-input path;
- a new secret transport.

`value_resource` is passed through to the existing browser/application protected-resource paths. Operation classification adds the existing `data-export` scope when a Computer Use action injects a registered local resource.

Browser Computer Use is classified under `browser-session`. Application Computer Use is classified under `application-control`.

## Current limitations

### Browser observation coherence

A current extension captures Chromium Accessibility, DOMSnapshot layout data, and the viewport screenshot inside one serialized `chrome.debugger` session. It also compares the top Page frame/loader before and after the CDP observation and revalidates the per-document extension epoch+URL for **every extension frame actually inspected** before accepting the complete capture. The frame recheck is one bounded batch over the observed frame ids rather than a fresh all-frame scan. A child iframe reload/replacement therefore invalidates the observation even when that frame returns to the same URL, preventing an old extension ref from being fused to a backend node from the replacement document.

A successful enhanced capture reports:

```text
capture.cdp = true
capture.navigation_coherent = true
capture.frame_epochs_coherent = true
capture.screenshot_source = cdp_surface
capture.atomic = false
```

`navigation_coherent=true` means no detected top-document replacement/navigation crossed the observation window. `atomic=false` remains deliberate: Accessibility, DOMSnapshot, and screenshot are sequential CDP commands, so ordinary in-document DOM/animation mutation can still occur between them. Computer Use retries one observation when a document replacement is detected and refuses the snapshot if coherence cannot be established.

The extension also performs a final `tabs.get` boundary check after semantic/CDP capture and the post-document epoch check. If the target tab has closed or become unreadable during observation, the entire snapshot is rejected instead of falling back to stale tab metadata captured at the beginning of the request. A returned browser snapshot therefore always refers to a tab that still existed at the final observation boundary; action-time preflight independently repeats tab existence, URL, document-epoch, and target checks.

The CDP observation is component-aware rather than all-or-nothing. `capture.cdp_components` records whether layout metrics, DOMSnapshot geometry, Accessibility, and the requested screenshot succeeded. If DOMSnapshot fails, Accessibility nodes are retained but may lack bounding boxes/action-ref fusion. If the CDP screenshot alone fails, the Accessibility tree is retained and the image can fall back to `captureVisibleTab` **only when the target tab is already the active tab in its window**. Computer Use never activates an inactive target merely to obtain this legacy screenshot: the fallback calls the screenshot helper in an internal non-disruptive mode that forbids tab switching. The target is checked as active again inside that helper; if the user switches before/during capture or the optional fallback capture otherwise fails, Computer Use discards the image, records a bounded `capture.screenshot_fallback_reason`, and keeps the already-valid semantic/CDP components subject to the normal final document/tab coherence checks. This avoids pairing a pre-activation semantic tree with rendering/page state changed by `visibilitychange` or focus handlers. Because any visible-tab fallback image is not the screenshot from the serialized CDP capture, `screenshot_source` is not `cdp_surface` and the snapshot is deliberately ineligible for visual point dispatch.

If the debugger cannot be attached at all (for example another debugger owns the target) or an older paired extension lacks `computer_observation_v1`, Computer Use falls back to the existing DOM semantic inspection. A visible-tab screenshot is added only under the same already-active rule above. The fallback is explicitly marked in `capture.fallback_reason`, an intentionally skipped image in `capture.screenshot_fallback_reason`, and the observation never pretends to contain a Chromium Accessibility tree. Because `captureVisibleTab` identifies only a window rather than a tab, the extension also proves that the requested tab is active immediately before **and** immediately after the capture; if the user switches tabs across that boundary, the image is discarded instead of being mislabeled as the requested tab. The separate explicit `browser_screenshot` tool may temporarily activate its requested tab because screenshot capture is the caller's direct goal, but it first requires a previous active-tab restore baseline and revalidates immediately before activation that the same baseline tab is still active. If the user switched tabs during preparation, the screenshot fails definite pre-dispatch and does not activate anything. Once the activation API has actually been invoked, a rejected activation response is ambiguous: capture stops, no rollback is attempted, and the caller must inspect the tab inventory before retrying because the activation may already have happened. After activation resolves successfully, the pre-capture active-tab check, capture, and post-capture active-tab check share one `try/finally` restoration lifecycle. A successful explicit screenshot takes its returned title/URL from that verified post-capture active-tab observation and reports `tab_metadata_verified=true`; it never reuses provenance resolved before capture. Restoration first re-reads the active tab: if the target is still active it restores the original baseline and verifies that restoration; if the user has switched to a third tab it preserves that user choice; if active-tab state cannot be verified or restoration fails, the request fails closed. Failure or uncertainty about capture identity or restoration is returned as a fixed safe error rather than silently returning pixels from the wrong tab or overwriting the user's browser state.

The new extension capabilities are feature-detected rather than made mandatory in the extension handshake. A daemon upgrade can therefore continue to operate with an older paired extension; reloading the newer packaged extension enables the enhanced CDP path.

### Visual grounding and screenshot-bound points

Computer Use still reports `visual_grounding: false`: it does not ship or silently call a dedicated UI detector/model. A vision-capable caller can, however, use the screenshot returned by `computer_observe` and issue a snapshot-bound visual point for browser `click`, `double_click`, `hover`, point-to-point `drag`, or anchored `scroll`. The capability is advertised separately as `snapshot_bound_visual_points`.

Visual points deliberately use normalized viewport coordinates:

```text
target.point = { x: 0.0..1.0, y: 0.0..1.0, space: normalized_viewport }
```

They are accepted only when all of the following hold:

- the referenced observation actually returned a CDP surface screenshot;
- the observation detected no top-document navigation/replacement during capture;
- the top-frame document epoch is still identical immediately before dispatch;
- viewport width, height, and scale still match the snapshot;
- the visual viewport is not currently pinched/offset;
- the normalized point remains inside the current viewport;
- the exact screenshot SHA-256 still matches: inside the same serialized debugger attachment that will issue input, the trusted-input module recaptures the viewport with the original format/quality and rejects the action before any `Input.*` command when the bytes differ;
- trusted DevTools input is available. There is no DOM-event fallback for a point action.

Computer Use does not treat JavaScript scalar coercion as an alternate encoding of any of this authority. `surface`, `snapshot_id`, action, ref/resource names, input mode, waits, expectations, point coordinates/space, screenshot source/hash/quality, viewport dimensions, live tab URL/document epoch, and the private semantic-ref identity projection must arrive with the native JSON type produced by their source. For example `["click"]`, `["button-ref"]`, `[digest]`, `[0.5]`, `["complete"]`, or a string viewport width are invalid rather than equivalent to their scalar contents. The last-hop browser ref precondition separately type-checks string identity fields and Boolean sensitivity/shadow fields; malformed snapshot or live identity becomes stale before any page/CDP mutation.

Immediately before trusted input, the extension performs a fixed `elementFromPoint` probe and returns a redacted semantic description of the hit surface when available. The probe is diagnostic rather than a claim that the visual target has a semantic DOM equivalent; canvas/WebGL remains a valid reason to use the point path.

The preferred routing remains:

```text
snapshot ref -> fused backend-node trusted input when available -> existing ref action path -> screenshot-bound visual point
```

Drag is deliberately implemented as one trusted-input settlement, not as a sequence of public mouse calls. The browser extension emits a bounded `move -> press -> interpolated moves -> release` CDP sequence with the left-button bit held across intermediate moves. If any command after input starts fails or loses its response, the whole drag is an unknown outcome and is never replayed through another path. The trusted-input layer attempts a best-effort release after an interrupted drag so a failed request does not intentionally leave a virtual button held, but that cleanup does not make the business outcome definite. Ref drag also refuses to auto-scroll either endpoint: scrolling one endpoint can invalidate the other's snapshot geometry, so callers must first establish a snapshot where both endpoints are visible. This keeps the observe-to-act proof stronger than convenience-oriented drag helpers that silently mutate scroll state before the gesture.

Scroll follows the same settlement rule but is intentionally a **single** CDP wheel mutation. The caller supplies bounded CSS-pixel `delta_x`/`delta_y` and a same-snapshot anchor; `input_mode=dom` and `wait_for` are rejected before dispatch. The extension sends exactly one `Input.dispatchMouseEvent(type="mouseWheel")` at that anchor. There is no fallback to `Input.synthesizeScrollGesture`, JavaScript `scrollBy`, DOM scrolling, or a second wheel attempt after that command has started: a lost response means the scroll may already have happened, so the outcome is unknown and must be inspected before another wheel action. A semantic ref anchor revalidates the extension-frame epoch, stable ref identity, and backend-node content quad and must already be visible; Computer Use refuses to call `DOM.scrollIntoViewIfNeeded` because that would be a separate scroll mutation and could change which nested container receives the subsequent event. A point anchor instead revalidates document, viewport, and the exact screenshot in the same trusted-input debugger session immediately before the one wheel command. This makes positioned scroll useful for virtual lists, nested panes, canvas, and custom-drawn surfaces without weakening snapshot provenance or replay safety.

For accessible child frames, a fused backend-node binding removes the old top-frame-only trusted-click limitation: CDP `DOM.getContentQuads` supplies viewport-relative quads directly, so Computer Use does not guess iframe offsets or equate extension numeric frame ids with CDP frame ids. Each private binding also retains the observed extension frame's document epoch+URL. Immediately before any backend-node trusted action, the extension re-reads `documentState` in that exact extension `frameId`; a same-URL iframe reload/replacement therefore becomes stale **before opening the DevTools input session**. CDP frame ids remain provenance only and are never assumed equivalent to extension frame ids. The same private binding also supports `press`, `type_text`, and `fill`: text actions use fixed `DOM.focus` on the backend node and then the existing trusted DevTools Input path. `fill` runs select-all, Backspace, and `Input.insertText` inside one dispatch-tracking scope, so a failure after any Input command is an unknown outcome and cannot silently fall back/replay. Registered `value_resource` data is still resolved only inside the daemon's browser operation service; the Computer Use kernel carries the alias and the extension receives only the transient resolved value, exactly as with the existing browser secret-input path.

A stable extension ref is not treated as sufficient semantic identity by itself. An SPA or virtualized UI can keep the same DOM element object while repurposing it from, for example, a `Save` button into a `Delete` button without replacing the document. Computer Use therefore carries a private bounded identity projection containing only non-value target identity fields (`tag`, `type`, `role`, accessible `name`, `id`, field name, label, placeholder, sanitized `href`, sensitivity classification, and open-shadow-root membership). The page-world ref route compares that identity after actionability lookup but **before** any focus, scroll, click, or value mutation. A fused backend route first revalidates its extension-frame epoch and then uses the same persistent extension ref to run a mutation-free identity check **before opening the DevTools input session**. A mismatch is stale-snapshot evidence and is never replayed through another input path. Mutable state such as `value`, `checked`, `enabled`, focus, and `bounding_box` is deliberately excluded so legitimate state and layout changes do not redefine the target's identity.

The older top-frame ref route follows the same replay rule even though its preparation happens in the page world. `prepareAction` can focus keyboard targets or scroll pointer targets, so it is itself a side-effect boundary. In `auto` mode the extension checks that the fixed trusted-input module exists **before** calling `prepareAction`; only module absence at that point may fall back directly to one DOM action. Once page preparation has completed, debugger attach failure, trusted-input setup failure, cancellation, or any later trusted-input error is reported as an unknown/possibly partial dispatch even when the lower layer labels the Input portion safe to fall back. This prevents focus/scroll handlers from running once during preparation and then being followed by a replayed DOM action.

`wait_for` is strictly post-dispatch evidence, not part of deciding whether an action happened. Once navigation, a page action, a snapshot-bound backend action, or `fill_form` has returned from its mutating primitive, a later load/navigation wait timeout, cancellation, or tab closure is reported as `action outcome is unknown` and is never converted into trusted-input fallback or another DOM action. Computer Use therefore captures post-state and requires replanning instead of replaying the mutation merely because the requested wait condition was not observed.

The extension-to-page mutation boundary is tracked independently from the broker transport. Loading the fixed page module remains a mutation-free setup step, and cancellation is re-checked after that setup completes before the mutating page invocation is allowed to start. The page module carries an explicit internal version: reinjecting the same version preserves its document epoch and ref registry, while an older or unversioned isolated-world instance is replaced before use; the mutation wrapper also verifies the expected version before calling any page mutation API. The subsequent `scripting.executeScript` call that invokes `action`, trusted `prepareAction`, `fillForm`, or `uploadFiles` returns a small settlement envelope when the page function itself completes or throws. That preserves definite errors such as stale refs or invalid fields. If the scripting invocation itself rejects or returns no settlement after it has been attempted—for example because navigation destroys the execution context after a click—the page mutation may already have run, so the extension emits the fixed unknown-outcome signal and never automatically re-invokes the same page mutation.

Cancellation is also checked at each browser mutation-stage boundary, not only when the request first enters the extension. If cancellation arrives while an asynchronous target lookup or mutation-free preparation read is pending, the next mutation primitive is not invoked. In a multi-stage operation, already-completed stages are preserved rather than rolled back: cancellation after a tab has been activated stops a later window-focus mutation; cancellation after ref `prepareAction` can stop DevTools Input even though focus/scroll preparation may already have produced page effects. Snapshot-bound backend actions apply the same rule around asynchronous AX/geometry reads: cancellation during a pre-focus checked-state or off-screen geometry read prevents the later focus/scroll stage, while cancellation during the post-focus checked-state recheck suppresses the Space key but preserves the earlier focus as an unknown action outcome. Trusted DevTools sessions also gate cancellation after any same-tab session queue wait and before `chrome.debugger.attach`, so a cancelled queued request does not attach the debugger merely because an earlier request held the tab session. Top-frame trusted page actions and snapshot-bound visual point input carry the same gate through to the first `Input.*` command; visual point input additionally rechecks after screenshot-digest revalidation, so cancellation during that read-only verification cannot start trusted input. Explicit screenshot capture uses the transactional variant of the same rule: cancellation observed after confirmed temporary tab activation but before capture skips capture and still enters the restoration `finally`, restoring the prior active tab when safely verifiable. These checks minimize new side effects after cancellation without pretending that an earlier stage did not happen.

The same rule applies one transport layer lower. For mutating browser RPCs, once the owner request registry or a proxy broker route has attempted the WebSocket send to the extension, a missing response no longer means “not executed”: timeout, socket loss, broker/extension replacement, or response-delivery failure is surfaced as a fixed unknown mutation outcome. The extension applies the same rule after a successful mutation has returned internally: if that mutating success result cannot be JSON-serialized or fit within the bounded extension response budget, the action may already have completed, so the extension returns a fixed unknown-outcome settlement instead of a definite serialization/size error. Sanitized extension/broker mutation settlements are converted to public, non-retryable `BridgeError`s before the direct MCP error boundary, while arbitrary read-only transport details remain non-exposed. Computer Use does not infer ambiguity from generic text such as `timeout` or even an arbitrary sentence containing `outcome is unknown`; it accepts only the fixed browser/application mutation-settlement prefixes, captures post-state when those markers occur, and keeps same-action retry disabled. Read-only browser RPCs keep ordinary transport and result-limit failure semantics, and an explicit extension preflight/error settlement remains authoritative.

The Chrome navigation mutation APIs themselves use the same conservative boundary. Request validation and target-tab resolution happen before mutation, but once `tabs.update({url})`, `tabs.reload`, `tabs.goBack`, or `tabs.goForward` has been invoked, a rejected Promise is treated as an ambiguous dispatch rather than proof that navigation never started. The extension emits the same fixed unknown-outcome guidance, Computer Use captures post-state, and `same_action_retry_allowed` remains false. Obvious pre-invocation errors such as a missing navigation URL still fail before the mutation API is called.

Tab metadata read after a settled browser action is deliberately weaker evidence than the action settlement itself. Navigation, legacy ref actions, screenshot-bound point actions, fused backend-node actions, multi-field form fills, and file uploads all perform one final `tabs.get` only to attach current tab provenance. If that read succeeds, the result carries `tab_metadata_verified=true` with current tab metadata. If it fails after the mutating primitive and any requested post-dispatch wait have already succeeded, the action remains successful, the result retains the target `tab_id`, reports `tab_metadata_verified=false`, and omits title/URL/window/status rather than falling back to metadata captured before dispatch. Computer Use preserves this evidence; an older paired extension that does not provide the field remains distinguishable as `null` rather than being claimed verified or unverified. A metadata-only read failure therefore cannot retroactively convert a successful mutation into a same-action retry opportunity.

The DOM fallback path uses the same side-effect accounting instead of treating page-world JavaScript as inherently replay-safe. A direct DOM action starts with mutation-free actionability lookup; desired-state no-ops, select-option lookup, and keyboard-shortcut validation happen before scroll, focus, click, or value mutation. Once a side-effecting step begins, any later exception is converted to the fixed unknown-outcome contract. Trusted `prepareAction` also marks failures after its focus/scroll preparation as unknown. Multi-field form operations preserve that boundary across fields, and file-input assignment/event failures do the same, so an agent never replays a DOM mutation whose page handlers may already have run. Packaged actionability polling does not depend on background-page renderer timers: its bounded 50/100 ms waits are serviced through a same-extension runtime message whose service-worker endpoint accepts only the current extension identity and integer delays from 1 through 250 ms. Failure of that timing service does not bypass stable-box or pointer-hit checks; it remains definite before mutation and becomes unknown after any side-effecting preparation step. The page-local `setTimeout` fallback exists only when no extension runtime messaging API is present, such as the pure unit fixture.

If backend geometry is unavailable before any side-effecting trusted step, `auto` mode may fall back to the existing ref action path; explicit `trusted` mode fails closed. Focus-based actions no longer perform a preliminary scroll: `DOM.focus` itself is the no-fallback boundary because focus handlers can mutate application/page state even before a keyboard `Input.*` command is sent. Pointer actions take the complementary route: they first read `DOM.getContentQuads` plus `Page.getLayoutMetrics` without scrolling. A missing/invalid viewport metric is treated as unavailable geometry, **not** as evidence that the target is off-screen, so it cannot trigger a speculative scroll. If the bound node is proven inside the visual viewport, trusted pointer Input proceeds without changing scroll state. Only a point proven outside a valid viewport enters `DOM.scrollIntoViewIfNeeded`; that scroll is also treated as a no-fallback boundary because scroll handlers, sticky UI, virtualization, and lazy loading may mutate the page. After a successful or ambiguous scroll, geometry is re-read before Input, but any scroll ambiguity, cancellation, later geometry failure, or trusted-input failure is reported as an unknown/possibly partial dispatch and is never replayed through the DOM path. Before either focus or scroll has been attempted, missing geometry/trusted-input support remains a safe `auto` fallback; a known missing/detached backend node remains stale-before-dispatch. Fused `check/uncheck` is a desired-state action at both layers. The daemon deliberately does **not** short-circuit an already-satisfied trusted binding from its earlier page-state evidence: even a no-op must pass the extension's current frame-epoch and semantic-ref identity gates. The extension then starts its fixed DevTools session with a mutation-free `Accessibility.getPartialAXTree` read on the snapshot-bound backend node. If the desired state already holds, it returns `coordinate_source=cdp_ax_state_noop` / `no_input_required=true` **without calling `DOM.focus` or sending any trusted Input command**. Otherwise it focuses the node, which becomes the no-fallback boundary, and immediately repeats the checked-state read before Space. Only if the state is still opposite does it dispatch Space exactly once. If the state converges while focus is being applied, no key is sent but focus may already have fired page handlers; if the post-focus state is indeterminate, the outcome is unknown and the DOM path is never replayed. Post-state verification remains mandatory, so neither no-key path is itself treated as proof of the final effect. Fused `submit` uses focus + Enter. `select` continues to use the existing frame-scoped DOM selection path rather than adding a less deterministic keyboard-selection protocol.

A future dedicated visual grounder should emit the same snapshot-bound normalized-point representation rather than introducing a separate unversioned coordinate API.

### Application screenshots and background input

macOS application observation now combines the existing Accessibility snapshot with a best-effort target-window PNG. The capture path is fixed and local: JXA gets the front Accessibility-window bounds/title and a bounded list of ordinary same-process CoreGraphics windows; the daemon matches those bounds so a front modal/dialog wins over a larger background main window. Window binding is fail-closed: the closest bounds must identify one unique CG window, or an exact front-window title must uniquely break an equal-bounds tie. If multiple windows remain indistinguishable, or several CG candidates exist while Accessibility cannot provide front-window bounds, Machine Bridge refuses screenshot binding rather than trusting CoreGraphics list order. `/usr/sbin/screencapture -x -o -l <window-id>` then captures that exact window without activating or raising the application. The temporary PNG lives in a fresh system temp directory, is size/magic-validated, read into memory, and deleted in a `finally` block.

The application screenshot/Accessibility pair is still reported as `atomic:false`; Machine Bridge does not claim a native atomic snapshot primitive that macOS does not provide. Instead, the first fixed JXA call binds the target window, the exact window screenshot is captured, and the second fixed JXA call performs Accessibility inspection **then** re-runs the same front-window selection algorithm before that JXA process returns. This preserves screenshot → AX → post-AX window ordering while avoiding a third `osascript` launch. A stable id/bounds pair yields `window_coherent=true` and `coherence=window_screenshot_then_accessibility_window_stable`. Backends that do not support inline post-AX window state retain the separate `inspectApplicationWindow` fallback; production macOS AppAutomation uses the inline path. Geometry collection also propagates each AX element's owning `AXWindow` bounds privately; window-local boxes are emitted only when that owner matches the captured window. This prevents a same-process sibling window that overlaps the screenshot in global coordinates from becoming a visual-point candidate. The owner-window screen bounds are stripped from the public projection. If the window changes during capture, the screenshot and AX text remain useful evidence but window-local AX geometry is removed, `window_coherent=false`, and both semantic-point and native pixel-point capabilities are disabled for that snapshot. If window revalidation itself is unavailable, the observation says `window_coherent=null` / `window_screenshot_then_accessibility_unverified`; semantic point delivery stays disabled rather than treating unverified geometry as authoritative. Screenshot failure degrades to the single AX inspection with `atomic:true` and `coherence=accessibility_only_after_screenshot_failure`.

Application snapshots bind a private macOS **process instance** rather than treating PID as a durable identity. The fixed JXA helper resolves the selected `System Events` `unixId` and binds that PID to the public libproc `PROC_PIDTBSDINFO` birth timestamp; its seconds/microseconds fields are encoded into the same opaque `proc:` generation token used by the fixed native input helper. A missing/failed libproc identity read is an authorization failure, not permission to fall back to second-resolution process metadata. Window selection, Accessibility inspection, post-AX window state, value verification, visual recapture, and native input must all match both PID and generation. These fields remain snapshot-private and are never projected in `computer_observe`, post observations, or ordinary `inspect_local_application` output. The native helper additionally retains the corresponding `NSRunningApplication`; transport classification consumes that retained instance instead of re-resolving by PID, SkyLight focus preparation rechecks the same instance after private PSN resolution and again before focus dispatch, and pointer-event boundaries revalidate it throughout the gesture. Even same-PID reuse therefore cannot inherit an old snapshot, transport choice, focus authorization, or in-flight gesture. If the process instance changes only after dispatch, post-state reports `process_changed=true`; effect verification refuses to let the replacement process confirm the old action, continuation does not map the old target, and an old-process exact-value handle is discarded without reading the replacement process.

The fixed macOS application helper requires both Accessibility authorization and macOS Automation permission to control `System Events`. Apple Events denial `-1743` is detected while resolving the target PID, before any application mutation is attempted, and is returned as a definite non-retryable `permission_denied` result rather than being misreported as a missing PID or ambiguous input outcome. Screenshot capture has the separate Screen Recording permission described below.

Application screenshot capture is a separate observation component. `computer_observe` attempts it by default when the application backend supports it, but failure never discards Accessibility state. Permission or capture failures are projected as fixed, path-free messages; Screen Recording permission may be required on macOS. Minimized/off-screen apps may have no capturable on-screen window. Application post-action observations intentionally disable screenshots by default so long trajectories do not accumulate redundant images.

Native visual point dispatch is **disabled by default**, even when a screenshot exists. The default macOS path remains Accessibility-first. An explicit experimental backend can be enabled with `MBM_MACOS_BACKGROUND_VISUAL_BACKEND=skylight-experimental`; ordinary runtime startup does not load or compile the helper or resolve private SkyLight symbols when that setting is absent. On first window capture after visual opt-in, the fixed helper is compiled into an owner-only runtime cache and probed once. Only a successful probe changes `snapshot_bound_visual_points` to true. The same fixed native binary is also used lazily for public PID-scoped keyboard delivery, but its `unicode_keystroke`/`key_press` operations bypass `SkyLightSymbols` construction entirely; using keyboard actions therefore does not opt into or probe the private visual backend. Probe failure degrades to screenshot + Accessibility observation and is surfaced through `visual_point_probed=true`, `snapshot_bound_visual_points=false`, and `visual_point_error_class`; it does not make observation fail. The native boundary itself accepts only an absolute runtime cache path, native finite coordinates/window bounds, native integer timeout/PID/window id, native string process generation/text/special key, and a native configured backend. Application screenshot point authority likewise requires an exact `macos_window` source, native PNG payload, native SHA-256/window id/bounds, and native normalized coordinates. A coercible array/object never enables the backend or reaches JXA/Swift input merely because `String(...)` or `Number(...)` would resemble the intended value.

Application screenshot points have a semantic-first delivery ladder. Computer Use claims `snapshot_bound_semantic_points=true` only when the snapshot's Accessibility candidate coverage is complete (neither the underlying AX traversal nor the salience projection was truncated) and the point lies inside exactly one enabled, addressable interactive Accessibility element. Before dispatch it re-captures and SHA-256-checks the exact window screenshot, performs a bounded full live AX reinspection with geometry, requires that coverage to remain complete, and recomputes all actionable same-window elements containing the point. The live point must still resolve uniquely to the exact selector/occurrence target from the snapshot; a newly overlapping Accessibility control therefore makes the snapshot stale even when the screenshot pixels did not change. Only then does Computer Use dispatch through the existing Accessibility action path (`coordinate_source=accessibility_point_resolution`). This works without enabling SkyLight and keeps visual targeting orthogonal to delivery. If coverage is incomplete, or zero/multiple actionable Accessibility elements contain the point, Computer Use does not guess: it uses the opt-in native pixel backend only when the original snapshot did not claim a semantic target and `snapshot_bound_visual_points=true`; an already semantic-bound point that becomes ambiguous at preflight is rejected as stale before input.

Snapshot-scoped application refs also preserve the source Accessibility traversal contract. The private snapshot records the observe-time `max_depth` and `include_menus`; ref preflight, semantic-point preflight, and AX dispatch reuse those exact settings so a duplicate selector's occurrence cannot be reinterpreted by a deeper/different traversal. `post_max_depth` and action-time `include_menus` affect only the newly captured post-action observation. Menu targets therefore must be observed with `computer_observe(include_menus=true)` before they can be addressed reliably.

When Accessibility geometry is available, application refs also retain the observed element's global `screen_box` and owning `AXWindow` bounds privately. Live preflight re-inspects geometry and rejects the snapshot if the nth selector has moved or changed owner window. The same expected owner/element bounds are then passed into the fixed JXA action helper; immediately before `AXPress`, focus, or value mutation, the helper recomputes the chosen element geometry and refuses dispatch if either bound changed. This turns occurrence/index into a snapshot-scoped identity aid rather than trusting it alone across sibling windows or reordered duplicate controls. The global bounds remain private and are never returned in the Computer Use element projection.

Discrete Accessibility state is read independently from optional content values. Computer Use always carries `checked`, `selected`, and `expanded` when the corresponding AX attribute has a definite Boolean state; unsupported state is `null`. Checkbox/radio `checked` is derived only from those roles' Boolean AX value, so `include_values=false` does not cause text fields or secure controls to be read for verification. Application expectations accept `target_checked`, `target_selected`, and `target_expanded`. A checkbox click with a known pre-state automatically expects the inverse checked state; a radio-button click expects checked=true; a disclosure-triangle click with a known expanded state expects the inverse. AX dispatch completion alone is insufficient: if the post observation does not show the expected state, the effect is `not_observed` rather than confirmed.

Application `check` and `uncheck` are stronger desired-state operations than `click`. `check` accepts an `AXCheckBox` or `AXRadioButton`; `uncheck` accepts an `AXCheckBox`. The snapshot must contain a definite checked state, and the fixed JXA helper re-reads that state at the last dispatch boundary after selector/window/element-geometry validation. If the desired state already holds, it returns `no_input_required=true` and sends no AXPress. Otherwise it sends exactly one AXPress and reports bounded `checked_before/checked_after` provenance. Computer Use always requires the corresponding post-state (`target_checked=true` for `check`, false for `uncheck`), even when the caller supplies additional explicit expectations; a contradictory expectation is rejected before input. Browser `check/uncheck` now applies the same non-weakenable desired-state expectation rule. Action matching itself runs with content-value collection disabled; discrete state readback is separate from optional text/value inspection.

The low-level Accessibility dispatcher validates text arguments before touching the application. Only `set_value` and `keystroke` accept `value`/`value_resource`; pointer, state, focus, and activation actions reject those fields before a registered resource is resolved, text actions reject a missing value before JXA runs, and `keystroke` additionally rejects an empty resolved string before mutation (while `set_value("")` remains a valid field-clear operation). Cancellation is re-checked after asynchronous registered-resource resolution and immediately before the fixed JXA mutation helper is invoked. Once a mutating Accessibility primitive starts, exceptions from activation, AXPress/click, focus, or AXValue assignment are reported as potentially partial dispatches. Keyboard actions deliberately use a two-stage boundary rather than posting CoreGraphics events from JXA. For `keystroke` and `key_press`, the fixed JXA helper performs only snapshot-bound selector/occurrence, owner-window/element-geometry, process-generation, and AX-focus preparation; the helper receives neither the Unicode text nor the special key. It returns the prepared PID/generation privately, and only after the target reports `focused=true` does the fixed native helper retain that exact `NSRunningApplication` and use public `CGEvent.postToPid`. Unicode text is split into at most 20 UTF-16 units without splitting a surrogate pair, and the native helper revalidates the retained process instance immediately before every key-down and again between each down/up boundary. Each down/up boundary uses a fixed 5 ms settlement gap; this is pacing, not replay, and the release fixture requires all three mixed CJK/emoji chunks to be consumed exactly once before the action is accepted as OS-level evidence. `key_press` maps only the documented layout-independent fixed key set plus optional Shift; command/control/option shortcut synthesis remains unsupported rather than guessed. Real inactive AppKit probes accepted mixed CJK/emoji text and fixed special keys while remaining non-key/non-active and keeping another process frontmost; multi-chunk delivery preserved order with zero activation. `input_transport=public-cgevent-pid` and `focus_prepared=true` are returned as dispatch provenance. Computer Use automatically requires the post-state `target_focused=true` for every ref-targeted `keystroke`, and a caller cannot weaken that intrinsic contract with `target_focused=false`; this verifies the deterministic focus preparation without pretending that arbitrary typed content itself was semantically confirmed. `key_press` does **not** inherit that postcondition because keys such as Tab/Shift+Tab intentionally transfer focus; its target is still required to be focused successfully before native dispatch, but any post-action effect must come from an explicit expectation or other evidence. A native helper response loss or failure after the first posted keyboard boundary remains an unknown, non-replayable overall keyboard outcome; a process-generation mismatch proven before the first native post never authorizes keyboard delivery. The same settlement boundary now extends across the local `osascript` transport: an explicit JXA preflight error remains definite, but after the mutating helper process invocation is attempted, process timeout/cancellation, missing output, or malformed JSON is an unknown action outcome because the Accessibility mutation may already have run. Fixed launch/Accessibility/visual unknown settlements are emitted as public, non-retryable `BridgeError`s so direct application-tool callers keep the inspect-before-retry instruction across the MCP error boundary; arbitrary JXA/preflight errors remain non-exposed. The Computer Use layer recognizes ambiguity only from an explicit allowlist of lower-layer mutation-settlement prefixes; generic words such as `timeout`, `osascript`, `accessibility helper`, or an unrelated sentence containing `outcome is unknown` are not independently treated as mutation evidence, so a resource or preflight failure before helper invocation remains definite. Computer Use therefore performs post-observation and effect verification instead of interpreting an exception after a mutation attempt as proof that nothing happened.

Non-sensitive application `set_value` also gains an intrinsic effect contract without returning the control value. Direct MCP `value` input is already immutable within the request, so Computer Use reuses that exact request value only inside the fixed read-only verification helper and does **not** duplicate it into retained-value storage; transient read-only verification transport failure may therefore be retried within `verify_timeout_seconds` without replaying the mutation. `value_resource` is different because re-resolving an alias could yield a different secret. For a resource-backed write, AppAutomation retains the exact value that was actually dispatched behind a bounded opaque `av_*` handle (maximum 32 live handles, 60-second monotonic crash/abandon fallback lifetime) **only when the live element returned by that same JXA dispatch explicitly reports `sensitive=false`**. The older snapshot's sensitivity classification is not sufficient: if the target becomes secure/sensitive between preflight and dispatch, no exact-value handle is retained. Computer Use never exposes the handle in MCP output. After the normal value-free post snapshot resolves the target again through its new private selector occurrence and geometry binding, a fixed internal `verify_value` JXA operation consumes that one-shot resource handle, compares the live AXValue locally, and returns only `supported/matched`; a second use of the handle fails. `computer_act` also runs idempotent best-effort cleanup in `finally`, so successful consumption, post-capture failure, target disappearance, and unsupported readback all release the retained resource value immediately during normal execution instead of waiting for TTL expiry. If a resource-backed write has an ambiguous dispatch and therefore no retained exact-value handle was returned, verification is deliberately inconclusive rather than resolving the resource alias again. A direct MCP `value` can still be safely compared after an ambiguous dispatch because the request value itself is the exact immutable input. The fixed JXA setter also classifies an exception from the AXValue assignment itself as a potentially partial dispatch rather than a definite pre-input failure. `target_value_matches=true` is mandatory for non-sensitive `set_value` even when additional expectations are supplied. If the private readback is supported and differs, the effect is `not_observed`; if readback is unavailable, effect remains `unknown`. Targets classified sensitive (including `AXSecureTextField`) do not retain or enable this intrinsic readback and reject explicit `target_value_matches`, so secret-field writes still require another safe external post-condition when effect confirmation is needed.

- macOS application Accessibility elements include window-local geometry when a window capture is available. `focus_query` scans a bounded larger AX candidate set, ranks by task relevance/focus/actionability/visibility, and returns only the requested budget; sorted `aN` refs retain private bindings to the original selector occurrence so ranking cannot retarget duplicate controls.
- `focus_query` is evidence-bearing rather than merely a ranking hint: application and browser DOM observations report match count and whether the bounded search was exhaustive. Chromium AX reports matches too, but its depth-bounded tree conservatively reports `query_search_exhaustive=false`; a query miss therefore never proves absence unless the relevant observation channel explicitly says the search was exhaustive.
- opt-in macOS application visual click uses snapshot-bound normalized window coordinates. The snapshot privately binds process generation, CG window id/bounds, and screenshot digest. `AppAutomationManager.pointApplication` immediately recaptures and compares generation/SHA-256/id/bounds, rechecks cancellation after that read-only validation, and only then enters the fixed native helper. The helper revalidates the same process instance and front window, stamps window/pid routing fields, and selects **one** PID event transport for the whole click: native AppKit uses `CGEvent.postToPid` with subtype 0 and deliberately skips focus preparation, while Chromium/Electron/Catalyst families use `SLEventPostToPid` with subtype 3 and perform bounded focus-without-raise preparation only when the exact target application instance is not already frontmost. A skipped focus is reported as `focus_without_raise=false`; once any focus-preparation mutation is attempted, including a partial focus failure, the provenance becomes `focus_without_raise=true`. If event-source creation then fails without any prior focus mutation, settlement remains definite pre-dispatch rather than being promoted to an unknown mutation. Once focus or pointer dispatch actually starts, later failure is unknown and non-replayable. The single-transport rule is evidence-driven: broadcasting one logical event through both routes duplicates delivery. The selected route is exposed as `input_transport` (`public-cgevent-pid` or `skylight-pid`). Raw global screen coordinates and global `CGEventPost` are not exposed.
- opt-in macOS application `double_click` is deliberately point-only and uses the exact same screenshot/window/process binding as visual click. It never approximates a double click as repeated `AXPress`, even when the chosen pixel lies inside one uniquely addressable Accessibility control. `ComputerUseManager` calls `AppAutomationManager.pointApplication` once with fixed `click_count=2`; the native helper keeps one transport and one click group, sends one move followed by down/up pairs with click state 1 then 2, and revalidates the target front window before every button boundary. A failure after either button-down is an unknown overall double-click outcome; the helper attempts one matching best-effort mouse-up when needed, but cleanup is not treated as evidence that either click succeeded or failed. The live AppKit release smoke requires exactly two additional `mouseDown` deliveries whose final click-count sequence is `[1,2]`, while another application remains frontmost and the hardware cursor remains unchanged.
- opt-in macOS application visual drag uses the same private process-generation/window-id/bounds/screenshot binding as visual click, but requires both source and destination to be normalized points from that one window snapshot. It never guesses a semantic Accessibility drag fallback. `AppAutomationManager.dragApplication` recaptures and hashes the window, rechecks cancellation, projects both endpoints into one screen/window coordinate system, and invokes exactly one native drag helper. Native AppKit drag now uses the same public PID route as AppKit click and deliberately performs no focus preparation; live testing with correct out-of-event-stream `NSEvent.mouseLocation` cursor evidence delivers exactly one down, eight drags, and one up without changing the frontmost application or hardware cursor when the target view accepts first-mouse delivery. AppKit may intentionally withhold a first mouse from an inactive-window view whose own policy rejects it; Machine Bridge does not transiently activate the app to bypass that policy and does not claim view-level effect from native dispatch alone. Chromium/Electron/Catalyst retain the SkyLight route and focus preparation they require. The helper revalidates the same process instance and front window at every event boundary and never changes transport mid-sequence. Any failure after focus or pointer dispatch starts is unknown and non-replayable; after an interrupted post-down sequence the helper attempts one best-effort mouse-up cleanup without treating cleanup as effect evidence.
- opt-in macOS application visual scroll uses one normalized point from the same exact window screenshot plus bounded `delta_x`/`delta_y` values. Positive deltas keep the public Computer Use convention used by browser scroll (right/down); the native helper reverses those values only at the final macOS wheel mapping because CoreGraphics uses the opposite reveal-direction convention. `AppAutomationManager.scrollApplication` revalidates process generation, window id/bounds, screenshot SHA-256, and cancellation immediately before dispatch. Scroll keeps one fixed `skylight-pid` event transport because that route has the strongest live wheel evidence, but native AppKit targets skip focus preparation; Chromium/Electron/Catalyst retain it. The helper primes the same window-local point once, revalidates the same process instance/window, and emits one precise pixel-unit wheel event with no AX-center, keyboard, second-route, or foreground fallback. The release smoke uses a real nested `NSScrollView` and requires one precise wheel event, exact signed delta, visible post-state change, and the expected content-offset movement while the fixture never becomes active and the hardware cursor remains unchanged. Any uncertainty after actual focus/input begins is non-replayable and must be inspected from the post snapshot before another scroll.
- native visual focus/cleanup is concurrency-aware and non-disruptive best effort. SkyLight focus handling is decided from one captured `priorFront` application instance, and that exact frontmost instance is revalidated before the SkyLight path can continue. If the target was already frontmost, no focus mutation is sent but a concurrent user switch still causes a definite pre-dispatch failure. A background target is allowed to enter focus preparation only when there is a live, stable non-target `priorFront` restore baseline; a nil/terminated baseline fails before mutation. Before private focus preparation, `_SLPSGetFrontProcess` must resolve to the same PSN as `GetProcessForPID(priorFront.processIdentifier)`, while the retained target process instance and frontmost baseline are rechecked, so disagreement between AppKit/Workspace identity and SkyLight front-process state cannot authorize input. The helper then performs a last-hop front-process reread immediately before the first private defocus event. If that first mutation reports failure, it stops without attempting the second target-focus event; otherwise it re-resolves the target PID→PSN and retained process instance immediately before target-focus. At that second boundary, any concrete `NSWorkspace` frontmost application must still be either the captured `priorFront` or the target; a third application means the user won the race and target-focus is not sent. A temporarily nil frontmost value is tolerated during the helper's own defocus transition. The 50 ms focus-settlement delay runs only when focus mutation actually started, so AppKit/no-focus and already-frontmost paths do not pay it. After that conditional focus-settlement delay and before any pointer event source is used, SkyLight-framework paths revalidate the frontmost application without defeating focus-without-raise semantics: if no helper focus mutation ran, the already-frontmost target must still be frontmost; after background focus preparation, the current frontmost instance may be either the captured `priorFront` or the target, but never a third application. The same frontmost authorization is then combined with process-instance/window revalidation at every pointer boundary, including double-click button boundaries and every drag step, so a later user switch to a third application stops the remaining gesture rather than being ignored. Native AppKit uses the public framework policy and therefore keeps its proven non-frontmost background-input path. Settlement tracks focus dispatch and pointer dispatch independently: a boundary or event-construction failure that occurs before either mutation remains definite pre-dispatch, while any prior focus or pointer post makes the overall action unknown and non-replayable. If click/double-click/drag/scroll later becomes ambiguous after focus or pointer dispatch starts, the helper keeps the public result `dispatch_outcome_unknown`. Any required matching mouse-up is sent only while the original retained target `NSRunningApplication` is still the process behind that PID, so PID reuse cannot redirect release cleanup into a replacement process. The helper restores the previously frontmost application only when **this helper actually dispatched focus preparation** and the target application is still frontmost. Native AppKit click/drag/scroll skip focus preparation, so they never restore foreground state and cannot overwrite a concurrent user switch to the target app. Cleanup never converts an unknown mutation into success evidence, and a switch to any third application is never overwritten.
- macOS application `hover` is intentionally unsupported rather than emulated through an unreliable pointer fallback. A real AppKit tracking-area investigation showed that a PID-scoped synthetic `mouseMoved` can reach the exact target window and have `NSWindow.hitTest` resolve the intended view while `NSTrackingArea` still receives neither `mouseMoved` nor `mouseEntered`; the remaining AppKit tracking bookkeeping depends on state that per-process posting does not reliably reproduce. Computer Use therefore rejects application hover fail-closed instead of moving the user's hardware cursor, stealing foreground state, guessing an AX-center fallback, or reporting dispatch as semantic hover success. Browser hover remains supported through the browser trusted-input path.
- the SkyLight route is deliberately experimental because it depends on private macOS SPI and may break across OS releases. The helper source is fixed in the package, hashed before compilation, compiled lazily into an owner-only cache, and exposes no caller-selected symbol/event surface. Concurrent callers share an in-flight compiler setup, but cancellation is owned by the call that started that build: an uncancelled waiter does not inherit another call's cancelled `swiftc`, and instead rebuilds under its own context before probing. Capability probe results are cached when they settle as real availability/unavailability evidence, but a cancelled probe is propagated without updating that cache so one transient caller cancellation cannot make the backend appear persistently unavailable. Application launch, mutating Accessibility JXA, and native input helpers use the shared process runner's explicit non-replayable settlement boundary: cancellation, policy denial, or spawn failure proven before a child process starts remains definite and is never mislabeled as input ambiguity. After spawn, timeout/cancellation, process-error response loss, or a nonzero launcher/JXA exit is non-replayable unknown because side effects may already have occurred. The native pixel helper intentionally runs with `allowFailure=true`, so a nonzero helper exit still returns its structured `dispatch_started` settlement for more precise caller-side classification instead of being flattened into generic unknown. A manual disposable AppKit smoke harness is provided for release/OS validation and is not part of normal CI or startup.

The manual smoke requires two independent opt-ins and uses only a disposable accessory AppKit fixture:

```sh
MBM_MACOS_BACKGROUND_VISUAL_BACKEND=skylight-experimental npm run macos-background-input:smoke -- --run
```

The smoke compiles the fixed fixture into a fresh disposable `LSUIElement` `.app` and launches it through LaunchServices with `open -g`, because raw spawned AppKit binaries can own a WindowServer window before System Events exposes a usable Accessibility tree. To keep release validation aligned with the production surface, it tests **ComputerUseManager end to end only** instead of maintaining parallel release harnesses: coherent observation/process-generation binding, idempotent `uncheck`, `check` through the mapped post-snapshot ref, non-sensitive direct `set_value` with retry-safe private value readback, three-chunk mixed CJK/emoji `keystroke`, one exact `Shift+Tab` `key_press`, semantic-ref focus, raw visual click, exact double-click click counts `[1,2]`, exact 1/8/1 drag, and one verified scroll effect. The fixture records its own `applicationDidBecomeActive` count; it must never increase, the fixture must not be frontmost at completion, and every native visual gesture must preserve the hardware cursor. Unrelated user switches between other applications are allowed. Cleanup restores the original app only if the fixture itself is frontmost, terminates only the fixture-published PID, and removes the whole disposable directory. This single smoke is a deliberate OS/release check rather than normal CI.
- Application visual action results also report up to four snapshot-local `semantic_point_candidates` whose window-local AX boxes contain the chosen point, smallest region first. This is provenance only: an empty/ambiguous candidate set remains valid for canvas/custom UI and never substitutes for screenshot-bound dispatch or effect verification.
- Post-action screenshot policy is shared across browser and application surfaces: `auto` emits visual evidence only for visual-point actions, explicit `expect.visual_change`, or ambiguous dispatch; ordinary semantic/Accessibility actions stay image-free. Application `expect.visual_change` compares window-screenshot SHA-256 fingerprints and never treats visual change as success unless explicitly requested.
- Application post-state now defaults to a compact summary too. It retains up to 24 salience-ranked post-snapshot refs plus the bounded semantic delta, so long trajectories can continue from `post_snapshot_id` without replaying the full AX tree; `post_observation_detail=full` remains available explicitly.
